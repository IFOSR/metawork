## Execution

**The Executor's web tools prefer DeepSeek, stop scraping Baidu, and count what
they bill.**

- `web_search` calls DeepSeek's Search API (`POST /v1/tools/search`) whenever a
  DeepSeek Provider credential is configured, and falls back to Bing HTML when
  there is no key, the query exceeds the 128-character API limit, the request
  fails, or it returns no usable result. The terminal failure still reports the
  existing "network unavailable / anti-bot" contract with both backend reasons.
- The DeepSeek credential is the Provider key:
  `resolveRuntimePrivateConfigurationBinding` injects `DEEPSEEK_API_KEY` and
  `DEEPSEEK_SEARCH_BASE_URL` from the enabled DeepSeek Provider (by ref or by
  `api.deepseek.com` base URL). No separate search key exists, and an
  unresolvable credential degrades to Bing instead of failing the attempt.
- Results keep the `data.web[]` shape and add `site`, `publishedAt`, `authority`
  and `rerankScore`; `provider` reports `deepseek-search-api`. Per-call cost is
  exposed as `estimatedCostUsd` (0.00075) in tool details.
- The Baidu HTML backend is removed entirely (`parseBaidu`, `www.baidu.com/s`).
- `web_fetch` is routed by affordance: attempts with `public-web-search +
  public-web-fetch + source-citation` fetch through DeepSeek's extraction API
  (`deepseek-fetch-api`, server-rendered Markdown, private targets refused
  server-side), while other attempts keep curl so a workspace task can still read
  a local service it started. DeepSeek 402/429/5xx/network failures fall back to
  curl; 401/403/404/413 return a terminal, actionable error.
- Bounds: DeepSeek 20 s search / 30 s fetch with at most two attempts, unchanged
  Bing 5 s connect / 15 s total, unchanged 30-search budget per attempt and
  in-attempt result cache.
- The Planner/Manager tool surface is unchanged: research stays Executor-owned and
  the Manager still has no web tools.

## Billing usage

- Each billable DeepSeek request is recorded as its own metered observation on the
  attempt's Query: `search` for `web_search`, `tool_request` for `web_fetch`,
  metric `request`, quantity 1. Free fallbacks, rejected URLs and non-web tools
  are never counted, and no price is attached to a measured quantity.
- The account usage view adds a "联网检索" block with search and fetch counts next
  to the Token summary; the counters are read from the same durable observation
  store, scoped by account and the selected period.
- Token projections are unchanged: tool requests carry no model identity, so they
  never enter Token totals or quota.

## Verification

- `npx tsc --noEmit` and the Web `tsc --noEmit` pass.
- Focused tests: Executor extension (14), Pi driver (26), Provider binding
  resolver (20, two pre-existing failures unchanged), usage normalizer, resource
  summary against a real SQLite schema (2), web usage service and management view
  (5), Web billing presentation.
- Regression baseline comparison before/after the change shows no new failures in
  `tests/executor`, `tests/metering`, `tests/storage`, `tests/management` and
  `tests/web`; the remaining failures are pre-existing (retired billing module,
  retired Codex driver).
- Live checks: real DeepSeek search/fetch through the packaged Pi 1.5.0 and
  through the live configuration revision returned `deepseek-search-api` with
  publication dates and `deepseek-fetch-api` extraction; a real 美国禁飞 research
  attempt ran 11 searches and 18 fetches entirely on DeepSeek with no fallback.
- Web acceptance: the new usage block was verified against a preview Server
  (`/api/usage/timeline` returns `web: { searchRequests, fetchRequests,
  totalRequests, available }`).

## Known limits

- Search billing is tracked as request counts, not money: no pricing table is
  attached to usage facts, and `web_fetch` has no independent per-attempt budget.
- `ori_question`, domain/language/recency filters and `need_content` are not
  exposed as tool parameters yet.
- Historical attempts recorded before this version have no search usage.
