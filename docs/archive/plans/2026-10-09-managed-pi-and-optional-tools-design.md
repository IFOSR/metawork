## 1. 产品边界

Pi 执行工具是 MetaWork 的必需执行组件，由 MetaWork 随包提供、验证和维护。
用户安装 MetaWork 后不再单独安装 Pi，也不需要寻找路径。配置模型等业务设置仍
在应用内完成，“执行组件就绪”不等于模型凭据已经配置。

Codex 是可选外部工具，由用户安装、升级；MetaWork 负责自动发现、手动路径配置、
兼容性检测、调用和官方安装指引。未来 Claude Code 等按同样方式接入，不自动随包打入，
也不宣称本期已经支持。是否打包以产品必需性决定，不随支持工具的数量增长。

内部 `planner/AnyFusion-Pi` 是定制 Planner/TUI 组件，继续独立构建并随应用发布。
它与 Pi 执行工具用途不同，不能相互作为缺失时的替代程序。Node、SQLite 和现有
Pi PDF 扩展/Python 等应用依赖继续按正式发行契约管理和验收。

v0.1.8 已经包含 Pi 执行工具。本版保持这一分发方式，修正工具选择、更新健康检查和
故障恢复；不采用上一版“移除 Pi、要求用户额外安装”的提案。

## 2. Pi 的位置、选择和用户已有 Pi

- 打包一份经过验证的 Pi 与依赖，随 MetaWork release identity 固定版本和校验值。
- 从安装包部署到当前受管理的 Runtime 发布目录，实际执行使用该发布对应的绝对入口。
  后台不直接依赖已被退出、替换或移走的 Applications 应用目录来运行 Pi。
- 设置检测、执行器 probe、真实任务启动共用同一入口和配套 Node；不再各自搜索裸 `pi`。
- 用户电脑已安装的 Pi 不作为默认候选，不因它较新而自动切换，也不覆盖或卸载它。
- 不在用户全局 PATH 中注册内置 Pi；终端原有 `pi` 的选择不变。
- 任务继续使用 MetaWork 隔离的 HOME、配置和会话，不自动导入个人 Pi 的插件、凭据和会话。
- 普通设置页不提供“安装 Pi”或 Pi 路径输入框；本期不新增高级 Pi 替换功能。

同一安装的多个智能体、Desktop/Web/TUI 共用这份执行组件，不为每个智能体复制一份 Pi。
安装包源与部署后的 Runtime 可以各持有一份，这是当前离线部署/恢复成本；实际总占用
应测量 app、Runtime、暂存和清理后的结果，不能把 Pi 文件大小当作用户机器唯一占用。

## 3. Pi 更新随 MetaWork 发布

Pi 上游发布新版后，研发评估其收益与兼容性，测试参数、输出协议、隔离会话、模型调用、
PDF 扩展及真实任务，通过后将选定版本纳入下一个 MetaWork 版本。
发布说明列出 Pi 版本和已适配的重要变化；用户只更新 MetaWork。

应用内不运行 Pi 自更新、不后台拉取“最新 Pi”、不通过另一更新器修改已签名 Runtime。
更新前遵守已有任务静止/排空规则；应用、Runtime、Pi 作为一致组合切换和恢复。
旧 Runtime 及其 Pi 只按事务恢复需求暂存，成功后按正式清理规则处理，不出现额外可见应用。

上游新功能不会自动全部出现在 MetaWork 中；新协议/新能力由适配器和能力证据接入。
研发可因 Pi 的重要修复单独发 MetaWork 补丁版本，但无须跟随每个上游小版本立刻发版。

## 4. Codex 等可选工具

优先验证用户保存的路径；未配置时通过统一的主机工具发现能力检查用户 PATH、常见目录和
包管理器入口。macOS shell PATH 读取必须有超时和已知目录回退，Finder 与终端结果一致。
不扫描整盘、不搜索当前目录、不把 MetaWork 历史缓存中的工具误认成外部安装。

发现有效程序后展示来源、版本、路径，不自动启用智能体。自动模式使用 Server 启动时
统一导入的 PATH 按确定性优先级解析绝对入口，不批量改写旧配置；用户选择的绝对路径
通过空闲期配置激活保存。允许改选；手动路径失效不静默换工具。

手动选择保存稳定的绝对入口，允许包管理器符号链接；检测其目标变化、版本、执行权限和所需
解释器。检测和实际启动消费同一解析结果，使用结构化参数，不执行用户输入的 shell 字符串。
shim 必须在 Finder 和隔离任务环境中可运行，不能借用用户真实 HOME 绕过隔离要求。

用户通过原安装渠道更新 Codex，MetaWork 在检测/调用前重新验证变化。已知不兼容时只
将对应工具标为不可用；不自动升级或降级用户程序。未知版本需进行协议能力验证，不能
仅因 `--version` 成功就声称所有功能、模型授权均可用。

## 5. 设置体验

执行工具独立于智能体定义，一个工具可供多个智能体共用。

| 卡片 | 正常状态 | 操作 |
| --- | --- | --- |
| Pi · 内置 | 已就绪；随 MetaWork 更新，无需单独安装 | 默认仅显示状态；版本可查看详情 |
| Codex · 可选 | 已就绪/未找到/不可执行/版本不兼容 | 自动检测、选择程序、安装指引 |

Pi 异常时显示“执行组件暂不可用”，说明恢复进展；恢复失败再显示“重试恢复”和明确
原因。此动作修复组件，不与“完成更新并重启”混用，不要求用户理解 Pi 安装目录。
没有故障时不展示修复按钮，不把大量维护操作加入应用菜单。

Codex 路径先验证再进入设置草稿，仍通过现有“保存并激活”事务生效；程序路径/环境
切换遵守严格空闲门；逐任务读取版本化绑定，因此不额外重启后台，不在任务执行中途修改实际调用程序。
未安装时提供按平台组织的官方安装指引，安装后“重新检测”，本期不代用户运行安装脚本。

“必需/可选”是产品级要求，“哪些智能体需要该工具”另行展示。启用 Codex 智能体不使
Codex 变成全局必需，也不能把 Codex 不可用的智能体静默替换成 Pi。
工具就绪和模型/授权就绪分开提示。

Desktop 本地实例可选本机文件；Web 连接远程 Server 时路径属于 Server 主机，必须
标明目标。路径绑定/探测需要主机管理权限，不把任意主机程序启动能力开放给普通远程用户。

## 6. 安装更新与运行就绪分离

| 检查/场景 | 处理 |
| --- | --- |
| 用户机器没有全局 Pi 或 Codex | 安装/更新照常完成；使用内置 Pi，Codex 显示可选未安装 |
| 旧配置启用 Codex，但其路径失效或版本不兼容 | 保留配置，完成应用更新；对应工具未就绪，设置页修复 |
| 安装完成后受管理 Pi 缺失/无法启动 | 尝试受控恢复；应用仍可进入历史和设置，阻止依赖 Pi 的新工作 |
| 候选包签名/完整性失败，包括应有的 Pi 文件缺失/校验不符 | 候选包不合格，切换前拒绝；不能冒充安装成功 |
| 数据迁移、恢复检查、核心后台或认证界面加载失败 | 保留正式更新事务与回滚机制，报告明确诊断 |

工具可用性检查不再直接作为整个程序升级的健康门。发布包自身必须完整，且发布验收
必须证明内置 Pi 可运行；这与“用户没有安装外部工具不能导致更新失败”是不同要求。
对运行时权限/系统策略造成的工具故障，应用提供修复入口，不能无限重新应用同一更新。

Server 必须能在执行器未就绪时提供设置、历史和账号能力，不能隐式启动执行器才能通过
应用健康检查。Pi 不可用影响新工作接纳，不取消已接纳任务；Codex 故障只影响依赖它的工作。
任务失败、恢复和已授权 fallback 保持 Kernel 决策，不在界面或安装器新增恢复策略。

配置结构与权限验证继续严格。外部工具缺失不能阻止保存修复其他工具所需的合法设置；
现有绑定可保留为不可用，新选择的路径验证后激活，不能把不可用智能体视作可执行。
工具错误提供安全结构化原因，避免一律显示 `unexpected`，且不记录凭据/模型响应。

## 7. 受管理 Pi 的恢复

先确认失败类别：文件缺失、权限错误、组件校验失败、系统执行限制、解释器或协议故障。
仅对可恢复的组件文件损坏尝试恢复，不能把所有错误都处理为重复复制文件。

恢复只使用经签名/校验验证且与当前 Runtime identity 精确匹配的本地 payload。
应用包比运行中的 Runtime 更新时，不能从该包抽取新 Pi 塞进旧 Runtime；没有匹配来源时
提示通过完整 MetaWork 安装包恢复。不能从互联网下载任意最新 Pi 作为替代。

恢复复用 Installer 的锁、任务排空、暂存验证、原子替换和日志机制，不就地修改正在使用
的不可变发布目录，不绕过数据库/恢复约束。对一次故障只自动尝试一次；失败后停止并
提供诊断和重试入口，禁止无限循环，也不让多个客户端同时修复。

权限或系统策略阻止执行时给出针对性操作提示，既不假报恢复成功，也不要求安装另一份 Pi。

## 8. 旧安装与范围

- v0.1.8 继续使用随应用提供的 Pi，用户不需要额外安装步骤；模型、凭据和业务数据保留。
- 普通 Pi 绑定解析为当前受管理发布入口；不因用户全局 Pi 的版本改变而切换。
- 若历史配置显式指定了自定义执行入口，保留并明确标注；不得批量覆盖或改写历史任务绑定。
  恢复标准内置入口需通过已有配置激活，不另建临时兼容策略或新的普通 Pi 路径编辑流程。
- 旧启用 Codex 的配置不删除，路径发现修复与非阻塞就绪投影覆盖客户现有失败场景。
- 清理仅针对正式安装器管理的旧产物且遵守恢复生命周期，不删除个人 Pi/Codex 或用户数据。
- 当前只交付 macOS arm64 内部版，不新增 Intel、Apple Developer ID 或公证要求。
- 独立服务器发行包是否携带 Pi 由后续平台打包范围决定；本次不声称所有平台已经内置 Pi。

当前 Pi 文件逻辑大小约 121 MB，单独 gzip 约 31 MB，已在 v0.1.8 内，非本方案新增负担。
完整包大小仍以新版本实测为准；清理冗余依赖可另行优化，但不牺牲离线可用性和必要组件。

## 9. 所有权、契约与实施顺序

| 责任 | 唯一 owner |
| --- | --- |
| Pi 版本、来源、完整性、部署恢复 | Packaging / Installer / Upgrader |
| 可选工具路径草稿、版本化绑定、验证激活 | Configuration 与现有空闲门 |
| 工具发现和受控进程探测 | 主机工具 adapter；向应用/配置 owner 提供 port |
| 正式执行与失败规范化 | Executor driver / Execution；Kernel 保留恢复决策 |
| 就绪投影、设置 API、新工作接纳 | Application Shell / Management / Gateway |
| 状态展示和文件选择 | shared Web / Desktop platform adapter |

共享契约需要区分受管理工具身份与用户工具入口，并提供统一的解析/检测结果：
绝对入口、受控运行环境、来源、版本、状态及安全原因。消费者包括设置就绪服务、
配置验证、Executor driver 与安装诊断。工具身份不授予新权限或替代任务配置绑定。
账户配置保持隔离；不让一个账户路径修改影响其他账户，也不增加并行配置写入口。

删除相互独立的裸命令搜索、检测与真实执行路径分歧，以及把可选执行器缺失视为更新
失败的分支。保留现有数据迁移、完整性、锁、Kernel 恢复、历史配置和任务事实边界。

实施修订 ADR-0030 的健康分类、ADR-0033 的工具绑定/就绪激活、ADR-0045 的
受管理 Pi 与可选工具边界，同步 CONTEXT 和技术总览。阶段顺序：
统一实际调用入口 → 更新健康检查解耦 → 设置可选工具配置与 Pi 故障恢复 → 产物验收。
本期只交付本地验收产物，不触发 GitHub 发布。

## 10. 验收门

1. 全新 Mac 无全局 Pi/Codex：原样 DMG 经 Finder 安装后内置 Pi 可执行，模型稍后配置。
2. 用户有更旧/更新/损坏全局 Pi：仍运行受管理 Pi，个人配置/命令不受影响。
3. Codex 仅在用户目录、Homebrew、自定义目录或受支持 shim：发现、检测和真实调用一致。
4. Codex 缺失、权限不足、版本不兼容或探测超时：更新成功且可进入设置，不反复更新。
5. 管理的 Pi 运行时损坏：验证一次恢复、失败后停止重试、恢复源版本不匹配、任务忙碌和并发恢复。
6. 候选包缺少 Pi/校验失败：切换前拒绝；恢复不执行未验证或不同版本的组件。
7. 更换 MetaWork/Pi 组合：任务排空、应用/Runtime/组件一致切换、失败回滚、成功后清理。
8. 旧 preview 和 v0.1.8、启用 Codex 的旧配置：保留模型、凭据、对话、任务和历史绑定。
9. Pi 普通任务、PDF 扩展、Codex 任务在隔离 HOME 下真实执行，验证模型配置和工具就绪分离。
10. 重复启动、中断、磁盘/权限错误：互斥、数据恢复、进度和可操作诊断成立；无可见重复应用。
11. 客户端连远程 Server 时只配置授权的目标主机工具；普通用户不能调用任意本机程序探测。

交付记录须区分源代码测试、隔离环境测试、最终 Finder/DMG 验收和发布状态。不得把
开发环境中工具存在、单元测试通过或成功打开主页当作执行组件与升级可靠性的全部证据。

## 实施细化

Codex 程序路径按任务配置版本构建 adapter，不存在长期驻留的 Codex 进程绑定。
因此路径本身采用严格空闲门下的有限热激活，避免配置完成后再触发后台重启；
参数、driver、transport 等其他变动仍保持原重启约束（ADR-0033 修正）。
