# Web Settings Model And Agent Readiness Design

> **Status:** Approved
> **Design date:** 2026-09-16
> **Preserves:** ADR-0011, ADR-0020, ADR-0028, ADR-0031, ADR-0033
> **Amends during implementation:** ADR-0033 configuration presentation and
> credential storage contract

## Problem

The current Web settings surface exposes implementation vocabulary and
configuration details that ordinary users should not need to understand.

- The page is organized around `Provider`, `Planner`, `Executor`,
  `AgentClass`, and Harness terminology.
- Built-in executors are presented as product personas such as Pi Agent or
  Codex Engineering instead of user-owned agents.
- A custom Provider receives a generated technical name instead of requiring a
  memorable user name.
- Provider credential state exposes internal storage language while preventing
  straightforward API Key replacement.
- Planner and concurrency controls occupy the same visual level as the two
  concepts users actually need: models and agents.
- The product does not clearly detect whether the required local Pi CLI or the
  optional Codex CLI is installed, explain the result, or consistently block
  new work when the required agent is unavailable.

MetaWork is installed on a personal computer. This design deliberately
prioritizes a direct, editable local configuration over a complex credential
security subsystem.

## Goals

1. Present only two primary user concepts: **模型列表** and **智能体**.
2. Let users name and rename every model connection and agent.
3. Let users view a masked API Key state and replace any configured Key.
4. Store Provider API Keys in one directly editable MetaWork configuration
   file.
5. Detect required and optional local agent installations and explain how to
   resolve missing installations.
6. Require Pi for starting new work while keeping Codex optional.
7. Preserve model routing, capability configuration, and capability profiles
   on each agent.
8. Move only Planner and concurrency/queue controls into a collapsed advanced
   section.
9. Preserve current Kernel, routing, execution, recovery, and running-task
   semantics.

## Non-Goals

- Renaming internal `Provider`, `Executor`, `AgentClass`, `pi-agent`, or
  `codex-cli` contracts across the repository.
- Encrypting local API Keys or adding a user-facing secret manager.
- Automatically installing or upgrading Pi or Codex.
- Making Codex mandatory.
- Assigning engineering capability exclusively to Codex.
- Moving model routing or capability profiles into advanced settings.
- Terminating an already running Task because a later installation probe
  fails.

## Decision

### 1. User vocabulary

The settings page uses these labels:

| Internal concept | User-facing concept |
| --- | --- |
| Provider catalog | 模型列表 |
| Provider entry | 模型 |
| Executor / AgentClass | 智能体 |
| `pi-agent` | 智能体 1 by default |
| `codex-cli` | 智能体 2 by default |
| Planner and runtime policy | 高级设置 |

Internal IDs remain stable and are never shown as editable names. User-entered
names are presentation labels, not routing identities.

### 2. Settings information architecture

The page order is:

1. 模型列表
2. 智能体
3. 高级设置

高级设置 is collapsed by default and contains only:

- Planner configuration;
- concurrency and queue configuration.

Each agent card continues to own its existing:

- model selection;
- Fixed or Auto routing;
- allowed and fallback model pools;
- capability declarations;
- capability profile and manual.

### 3. Model list

Each model connection card shows:

- user-defined name;
- API base URL;
- masked API Key;
- discovered and selected model IDs;
- enabled state;
- connection or discovery result.

Adding a model opens a focused dialog. Name, API URL, and API Key are required
before the first save. The internal Provider reference is generated by the
application and is not editable.

After saving, MetaWork attempts model discovery. Discovery failure does not
discard the entered configuration or credential. The card remains editable and
shows a retry action.

Users may:

- rename the model connection;
- replace its API Key;
- change its API URL;
- rediscover models;
- enable or disable it;
- delete it subject to the existing routing-reference and activation rules.

The page does not display `Provider`, `SecretStore`, credential source, or
`apiKeyRef`.

### 4. Agent names

`ProviderDefinition` and `AgentClassDefinition` gain an optional
`displayName`. This is an additive configuration-schema change:

- new model connections require a non-empty display name;
- built-in `pi-agent` falls back to `智能体 1`;
- built-in `codex-cli` falls back to `智能体 2`;
- other legacy entries fall back to the current humanized internal reference;
- saving or renaming follows the existing draft, validation, compile, probe,
  and activation path.

The UI exposes only a normal name input. Users never enter a configuration path
such as `providers.<id>.displayName`.

Because the name is revision-scoped configuration, historical tasks retain
their pinned configuration identity. A rename does not change `providerRef`,
`agentClassRef`, Harness selection, or authorized bindings.

### 5. API Key storage

Provider API Keys are stored as plaintext in:

```text
~/.metawork/credentials.json
```

The path follows the configured MetaWork installation root. The default is
`~/.metawork/credentials.json`; an installation-root override places the file
at `<install-root>/credentials.json`. This design does not introduce a second
`~/.config/metawork` persistence root.

The file has one intentionally simple format:

```json
{
  "version": 1,
  "providers": {
    "openai": "sk-example"
  }
}
```

The implementation may retain `apiKeyRef` as an internal runtime binding
contract, but the reference is generated and resolved by MetaWork. It is not a
user-facing field and does not require the user to understand the backing
store.

The production credential adapter:

- resolves an internal Provider credential reference to one Provider entry;
- reads and writes only `credentials.json` after cutover;
- writes through a temporary file and atomic rename;
- creates the file with mode `0600` where supported without adding any user
  workflow;
- never copies a raw API Key into immutable configuration revisions;
- preserves the previous value when a replacement write fails.

The Web API returns only:

```json
{
  "configured": true,
  "maskedApiKey": "••••••••abcd"
}
```

Raw API Keys are accepted only on write and are never returned by a read
endpoint. An empty update means no change. Replacing a Key overwrites the
Provider entry after the file write succeeds.

The current configuration and Web credential endpoints may be simplified
together with their frontend consumers. There is no requirement to preserve an
obsolete response shape solely for compatibility inside this unreleased
surface.

### 6. Credential cutover

The cutover is deliberately small:

1. If `credentials.json` already exists, it is authoritative.
2. If it does not exist, startup makes one best-effort import of credentials
   referenced by the active configuration.
3. A successful import atomically creates `credentials.json`; subsequent
   reads use only that file.
4. If an old credential cannot be imported, the corresponding Provider is
   shown as missing and the user may enter it again.

There is no permanent dual-read adapter, migration state machine, or
user-facing secret-store selection. Old stores are not deleted automatically.

Deleting a model connection does not immediately delete its credential entry.
This keeps rollback to a historical configuration revision possible. Stale
entries remain visible in the directly editable local file and can be removed
manually.

## Agent Installation Readiness

### 1. Product rule

- Pi is a required local dependency for starting new work.
- Codex is an optional agent that improves model and execution choices.
- Pi may be configured for coding, research, image, or other supported
  capabilities. MetaWork must not represent coding as Codex-only.

When Pi is unavailable, users may still:

- start MetaWork;
- log in;
- select or create a Workspace;
- open existing Conversations;
- inspect history and results;
- open settings and repair the installation.

They may not:

- create a new working Conversation;
- send a new work request;
- admit new work through Web, TUI, Feishu, or another Gateway client.

Already admitted or running Tasks are not cancelled by an installation-status
change.

### 2. Readiness model

```ts
type AgentInstallStatus =
  | 'checking'
  | 'installed'
  | 'missing'
  | 'broken';

interface AgentReadiness {
  agentId: 'pi-agent' | 'codex-cli';
  required: boolean;
  displayName: string;
  status: AgentInstallStatus;
  version: string | null;
  detail: string | null;
  installUrl: string;
  checkedAt: string;
}
```

The `displayName` is resolved from the active configuration. `agentId` remains
the stable internal identity.

### 3. Ownership

A new `AgentInstallationReadinessService` belongs to the Application Shell
boundary. It is product environment diagnosis and new-work admission input,
not Kernel Executor health.

- It reuses the controlled executable and process-probe behavior of the Pi and
  Codex drivers.
- It does not mutate AgentClass health or recovery state.
- It does not schedule work or select an Executor.
- Management and Gateway surfaces project its state.
- Web never executes a local command.

Kernel-owned Executor health continues to describe revision-scoped runtime
availability after work reaches the existing routing and authorization path.

### 4. Detection behavior

MetaWork probes:

- once during Server startup without preventing history/settings access;
- when the settings page requests current readiness;
- when the user chooses 重新检测;
- once when the browser regains focus after opening an installation page.

Normal reads use a short TTL cache. Forced refresh coalesces concurrent probes
for the same agent. The service does not poll every second.

The probe uses the existing executable path and `execFile`-style invocation,
never a shell:

```text
pi --version
codex --version
```

Classification:

| Result | Status |
| --- | --- |
| Exit 0 with a parseable or non-empty version | `installed` |
| Executable not found (`ENOENT`) | `missing` |
| Timeout, non-zero exit, malformed launch, or unusable executable | `broken` |

Probe details are bounded and redacted before reaching clients.

### 5. Readiness API and events

Management exposes:

```text
GET  /api/agents/readiness
POST /api/agents/readiness/refresh
```

The first returns cached state and may initiate an asynchronous refresh when
stale. The second forces a coalesced refresh and returns the new state.

The existing WebSocket protocol gains:

```ts
{
  type: 'agent_readiness_state';
  agents: AgentReadiness[];
}
```

Startup, settings, the home-page initialization guide, the new-Conversation
action, and the composer consume this same projection.

### 6. New-work admission

Pi readiness is checked at the shared Application Shell admission seam before
a user input can create or advance new work. UI disabling is only guidance;
the Server remains authoritative.

When Pi is not `installed`, every applicable client receives:

```json
{
  "code": "required_agent_unavailable",
  "agentId": "pi-agent"
}
```

The same rule applies to Web, TUI, Feishu, and future Gateway clients. Query,
history, settings, Workspace selection, and installation refresh commands stay
available.

Codex absence never triggers this error. A configured Codex binding remains
unchanged, but it is not presented as currently usable until installation
readiness succeeds. MetaWork does not silently rewrite the user's routing
configuration.

## Web Presentation

### Required Pi card

The Pi-backed agent card presents one of:

- 检测中;
- 已安装, including version when available;
- 未安装, with “MetaWork 运行新任务所必需”;
- 已发现但不可用, with a bounded diagnostic.

Missing or broken states provide:

- 打开安装页面;
- 重新检测.

The installation action opens the maintained Pi coding-agent installation
page in a new browser tab. MetaWork does not execute a global installation
command.

### Optional Codex card

When Codex is missing, the card says that installation is optional and
explains concrete benefits:

- more complete native compatibility with OpenAI GPT/Codex model workflows;
- an execution path optimized for repository understanding, code changes, and
  test workflows;
- another agent choice for routing, task assignment, and fallback;
- complementary behavior alongside the Pi-backed agent.

It also states:

> Codex 是可选增强项。未安装不会影响 MetaWork 使用，智能体 1 仍可通过模型和能力配置完成代码、研究等任务。

Actions are:

- 查看安装说明;
- 重新检测.

The install action opens the current official Codex CLI documentation. The
implementation must keep installation URLs in one small catalog so they can be
updated without editing UI components.

### Global blocking presentation

When Pi is not installed:

- the home page shows an initialization banner linked to the agent section;
- create-Conversation and send actions are disabled with the same explanation;
- an attempted request that races with a readiness change renders the
  structured Server error and preserves the user's draft;
- successful re-detection removes the block immediately without a page or
  Server restart.

## Error Handling

- Invalid configuration never replaces the active revision.
- Model discovery failure does not discard a newly saved model connection.
- Credential write failure leaves the previous credential intact.
- Credential verification or model discovery failure is distinct from a file
  write failure.
- Malformed `credentials.json` is not overwritten automatically. Settings show
  the file path and parse error so the user can repair it.
- A probe timeout or launch failure is `broken`, not `missing`.
- A stale readiness response cannot reapply a block after a newer successful
  refresh.
- Browser focus refresh is opportunistic; the explicit refresh action remains
  authoritative.
- No readiness transition cancels an already admitted Task.

## Data Flow

```text
Settings UI
  -> existing configuration draft/activation API
     -> displayName + model/routing/capability configuration

Settings UI
  -> credential write/status API
     -> credentials.json

Server startup / Settings / explicit refresh
  -> AgentInstallationReadinessService
     -> controlled Pi/Codex version probes
     -> cached AgentReadiness projection
     -> HTTP + WebSocket clients

New input from Web/TUI/Feishu
  -> shared Application Shell readiness admission
     -> existing Session -> Planner -> Kernel path when Pi is installed
     -> required_agent_unavailable otherwise
```

No path lets the settings UI mutate Storage, schedule work, authorize an
Executor, or bypass configuration activation.

## Testing

### Configuration and credentials

- Provider and AgentClass display-name schema acceptance and validation.
- Legacy fallback names for Pi, Codex, and custom entries.
- Rename persistence across activation and restart.
- API Key create, masked read, replacement, failed replacement, and no raw Key
  in HTTP responses.
- Atomic `credentials.json` writes and malformed-file refusal.
- One-time import when the new credential file is absent.
- No credential duplication in configuration revisions or runtime events.

### Readiness service

- installed Pi and Codex with version projection;
- `ENOENT` classified as missing;
- timeout and non-zero exit classified as broken;
- TTL caching, forced refresh, and concurrent refresh coalescing;
- stale-result suppression;
- bounded diagnostic projection.

### Admission

- Pi missing blocks new Web, TUI, and Feishu work.
- Pi missing does not block login, Workspace access, history, settings, or
  readiness refresh.
- Codex missing never blocks new work.
- Pi recovery removes the block without restart.
- running Tasks continue when a later probe becomes unavailable.

### Web

- section order and default advanced-section collapse;
- no Provider, Executor, AgentClass, Harness, or SecretStore labels in the
  ordinary settings experience;
- model creation requires a user name;
- model and agent rename flows;
- masked Key display and replacement;
- Pi required-state banner and preserved composer draft;
- Codex benefit copy and optional state;
- installation links and focus/explicit refresh;
- routing, model selection, capability editing, and profile preview remain on
  the agent cards.

### Regression

- configuration validation, compilation, probing, activation, and rollback;
- model discovery;
- fixed and Auto routing;
- capability-manual generation and profile projection;
- historical Conversation and Task presentation;
- authorized running execution and recovery.

The product guide continues to use precise internal terminology for

## Acceptance Criteria

1. The ordinary settings page has exactly three top-level sections: 模型列表,
   智能体, and 高级设置.
2. No ordinary settings control requires the user to understand Provider,
   Executor, AgentClass, Harness, SecretStore, or `apiKeyRef`.
3. Every model connection and agent can be renamed without changing its stable
   internal identity.
4. Every Provider API Key can be replaced and is shown only as a mask in Web.
5. Provider API Keys are authoritative in one plaintext
   `~/.metawork/credentials.json` file by default, or
   `<install-root>/credentials.json` when the MetaWork root is overridden.
6. Planner and concurrency/queue controls are the only controls moved into
   advanced settings.
7. Pi is detected automatically and blocks only new work when unavailable.
8. Codex is optional, and its missing state explains the benefits of
   installation without diminishing Pi capabilities.
9. Installation recovery takes effect after re-detection without restart.
10. Existing configuration activation, routing, capability, history, running
    Task, and recovery behavior passes regression validation.
