## 1. 背景与问题

MetaWork 目前是一个功能完整的商业 Agent 产品，但它是在持续加功能的过程中长成的，没有经过一次整体收敛。结果是：

| 问题 | 用户可感知的表现 |
| --- | --- |
| **同一个概念有多套实现** | 产品同时存在 Web 端、桌面端、飞书和一个终端 TUI 形态，四套界面的能力与交互不一致 |
| **自维护的技术栈在落后** | 平台自研的 Agent 内核长期不更新，而它本可以跟随开源社区持续演进，用户拿不到上游的新能力 |
| **保留了已无价值的功能面** | 设置里存在一整套「模型价格」输入项，但产品并不按 token 售卖；账单页按每个任务出单，而用户根本不关心单笔任务花了多少钱 |
| **平台形态与用户场景不匹配** | 产品的定位是「解决用户本地电脑上个人助理型的问题」，但运行形态是本机 Server，重活干不了、也没法 7×24 在线 |
| **用户被问了不该问的问题** | 「成本优先还是质量优先」这类选择对普通用户没有意义；模型单价这种内部信息暴露在设置里 |
| **历史包袱压制每一次新改造** | 多轮升级累积的冗余逻辑、代码与设计文档，让后续任何优化都要先考古；改一处要先搞清楚「哪套是现役」 |

**核心判断**：MetaWork 现在缺的不是功能，而是**一次彻底的减法**。本文档定义减法之后的样子。

**本文档的阅读顺序**：
- **§2 项目体检与大扫除** —— 第 1 步，也是后续所有改造的前提。先看它。
- **§3 ~ §14** —— 产品本身该是什么样。
- **§15 ~ §19** —— 验收、待定、决策记录。

## 2. 项目体检与大扫除

> 这是本次改造的**第 1 步，也是所有后续改造的前提**。产品需求的每一项落地，都要先穿过这一层清理。

### 2.1 为什么要先做这件事

MetaWork 经历过多轮架构升级（Parser、Kernel、Work Graph、单 TUI 收敛、Account Runtime、多轮独立 Client……）。每一轮升级都是**加法为主**：新机制加上来，旧机制不敢删（因为还有测试、还有配置、还有文档在引用它）。结果是：

| 维度 | 当前存量（2026-11-07 实测） |
| --- | --- |
| 源代码 | `src/` 34 个模块、约 147,800 行 |
| 测试 | 约 138,300 行 |
| 数据库迁移 | schema 已到 **65 版**，`migrations.ts` 4,501 行、56 个迁移函数 |
| 兼容层 | `src/` 中带 legacy 语义的 **83 个文件**、502 处引用 |
| 设计文档 | `docs/` 共 **331 篇**、约 104,800 行 |
| └ 计划文档 | `docs/plans/` **188 篇**，其中 **79 篇已标注「已实施/已完成」**却仍留在活跃目录 |
| └ ADR | 45 篇，其中 24 篇互相提及「取代」，2 篇已标 Superseded 仍在活跃目录 |

**这些冗余不是中性的。** 它们会：

1. **让后续每一次优化都要先考古** —— 新人（或新 AI）改一处逻辑，要先在 104,800 行文档和 147,800 行代码里搞清楚「哪套是现役、哪套是历史」，成本极高。
2. **让错误判断难以察觉** —— 看到两套相似的实现时，无法区分「一个是旧的」还是「两个都有用」，于是不敢删，最终两个都留着。
3. **让测试变成负担而非保障** —— 大量测试保活着本该删除的旧行为，删除时反而要花大力气改测试。
4. **让架构重构的收益被抵消** —— 本次要做的一系列改造（换上游 Pi Agent、去掉审批层、收敛执行器、重做计费），每一步都会遇到「旧逻辑还在引用它」的阻力。

**结论：不清扫，就改造。每一次新的架构决策，都会立刻被历史包袱稀释。**

### 2.2 扫除范围

**FR-CL1.1 全面体检，不预设范围**
- 对**整个项目**做一次体检，不限于本次需求涉及的部分。
- 体检覆盖：源代码、测试、数据库 schema 与迁移链、配置模型、设计文档、构建与发布脚本、Docker 与安装脚本。
- 原因：冗余是全局的。只扫局部会留下跨模块的碎片，而碎片正是后续考古成本的主要来源。

**FR-CL1.2 三个判定维度**

每一处代码/文档都要用三个维度判定其去留：

| 维度 | 判定问题 | 结论 |
| --- | --- | --- |
| **是否在用** | 现在还有生产路径引用它吗？还是只有测试在引用、只有文档在提到？ | 无生产引用 → 候选删除（测试引用不算「在用」） |
| **是否是现役** | 它属于当前架构，还是上一代架构的残留？ | 上一代残留 → 候选删除 |
| **是否是唯一** | 同一职责是否还有另一套实现？ | 有重复 → 保留一套，删其余 |

**FR-CL1.3 只保留必要内容**
- 判定为「不在用 / 非现役 / 重复」的内容，**一律删除**，不保留「以防万一」。
- 原因：产品尚未发布，没有历史用户数据需要兼容。保留「以防万一」的代码会以两种方式伤害项目：一是让未来的判断持续受干扰，二是让真正的死代码混在活代码里无法识别。
- 验收：每一处删除都能说清「为什么可以删」；说不清的就不删。

**FR-CL1.4 兼容层随产品一起清退**
- 面向历史数据、历史配置、旧协议的兼容代码，随对应产品形态一起删除。
- 包括但不限于：旧 schema 的迁移分支、旧配置格式的读取器、旧事件/输出协议的兼容解析。
- 原因：产品未发布，兼容层没有存在对象。而每一段兼容代码都是一条需要永久维护、且每次改动都可能触发它的分支。
- 验收：不存在「仅为兼容历史数据而存在」的分支；数据库迁移链从当前版本直接升到新版本。

**FR-CL1.5 文档与代码同等对待**
- 设计文档与代码一样要体检。当前 188 篇活跃计划文档中，**79 篇已标注完成**却仍在活跃目录 —— 它们在持续制造「这件事到底做没做」的判断成本。
- 处理原则：
  - **已完成的计划** → 归档；
  - **已被取代的决策** → 归档，并在 ADR 索引里标注取代关系；
  - **仍然有效且仍被引用的** → 保留，但必须更新到与当前架构一致；
  - **从未被引用、内容已被现实覆盖的** → 删除。
- 验收：`docs/plans/` 中不再有已完成的文档；`docs/current/` 中每篇都能对应当前架构的一个真实切面。

**FR-CL1.6 只扫除，不新增**
- 体检与大扫除阶段**不引入新功能、不引入新的抽象层**。
- 原因：清扫与建设混在一起，会让「删掉了什么」无法追溯，也让清扫变成一个无底洞。清扫完再谈新增。
- 验收：清扫阶段的变更全部是删除或语义等价的重命名；任何新增的抽象都需要单独评审。

### 2.3 体检与扫除的产出

**FR-CL2.1 一份体检报告**
- 体检先于删除。产出一份清单，逐项列出：**位置 / 是什么 / 为什么判定为冗余 / 删除后影响什么 / 是否有替代**。
- 原因：直接删容易漏。先列清单再删，能保证「删过的」和「看过的」是一一对应的。
- 验收：清单覆盖体检范围内的每一个模块与文档分类。

**FR-CL2.2 删除按可独立验证的批次推进**
- 每一批删除必须**可独立验证、可独立回滚**，不允许「一把梭」大删。
- 原因：大爆炸式删除一旦出问题，无法定位是哪一处删除引起的，也无法回滚到可用状态。
- 验收：每批删除后完整测试通过；每批之间可以独立提交。

**FR-CL2.3 与产品需求改造合并排序**
- 清扫与产品改造共用一份实施顺序，按「依赖关系」排，而不是按「清扫 / 改造」分开排。
- 原因：两者高度耦合 —— 比如删掉计费链路必须先删掉价格字段，而价格字段的删除又在新的用量统计设计确定之后；把两个阶段拆开会做两遍功。
- 验收：存在一份统一的实施顺序，覆盖清扫与产品改造的全部条目。

### 2.4 已知的主要清扫目标（体检起点，非穷举）

以下是根据当前代码实测得到的高价值目标，体检时需逐项确认并扩充：

| 类别 | 已知目标 | 依据 |
| --- | --- | --- |
| **平台自维护的 Agent 内核** | 整个 vendored fork（约 104,500 行） | 落后上游 8 个 minor 版本；其中 77% 是要删的 TUI 客户端 |
| **第二个执行器** | Codex 全链路（约 1585 处引用、218 个文件） | 无差异化收益；只兼容自家模型 |
| **金额计费体系** | 价格字段、货币换算、按单出账、外部扣费链路（约 1,469 行纯货币逻辑 + 7 张表） | 产品不卖 token，不统计价格 |
| **审批层** | Kernel 的策略决策职责 | 派发已由决策模型给出结论，审批是重复确认 |
| **终端客户端** | 终端 TUI 全部实现 | 与 Web/桌面端功能重叠 |
| **Windows 路径** | 23 个文件、54 处分支 + 4 个安装脚本 | 用户占比低；Linux 已覆盖云端需求 |
| **兼容层** | 83 个 legacy 文件、schema 1→65 的迁移链 | 产品未发布，无兼容对象 |
| **已完成的设计文档** | 79 篇已标注完成的活跃计划文档 | 持续制造判断成本 |
| **现存 Docker 体系** | `docker/` 全部 + 4 个 Dockerfile + 2 个测试 + 2 个构建脚本 + 711 行 Docker 执行后端代码 | 镜像里固化的是即将被淘汰的 Pi 0.80.2 与已删除的执行器；详见 §2.5 |

**FR-CL3.1 体检必须发现清单之外的目标**
- 上表是起点，不是结论。体检应主动发现清单之外的问题 —— 重复实现、无人调用的模块、只有一个调用点的「通用框架」、命名已与职责脱节的模块。
- 原因：最有价值的清理目标往往不是事先能想到的。体检的价值就在于发现「自己也没意识到的东西」。
- 验收：最终清单中包含清单之外发现的条目。

### 2.5 Docker 的处置

**FR-CL4.1 删除现存的全部 Docker 资产**
- 当前仓库里的 Docker 体系整体删除，包括：
  - `docker/` 整个目录（运行时镜像、执行器 attempt 镜像、egress proxy、两套 entrypoint、Pi/Codex 配置与 env 样例、Windows 驱动脚本）；
  - 根级 `Dockerfile.test`；
  - `official-server/Dockerfile` 与 `official-server/Dockerfile.test`；
  - `planner/AnyFusion-Pi/Dockerfile.test`；
  - `tests/docker/` 下的两个测试；
  - 镜像构建脚本（`build-attempt-images.sh` / `.ps1`）；
  - 代码中的 Docker 执行后端与相关类型（`docker-cli-attempt-execution-backend.ts`、`container-compatibility-adapter.ts`、`container-cli` 驱动、`docker_socket` 权限项、Docker 标签对账逻辑）；
  - 文档中描述 Docker 部署与沙盒兼容路径的内容。
- 原因：
  - **这些镜像里固化的是被判定为要淘汰的东西。** 三处镜像各自 `npm install -g @earendil-works/pi-coding-agent@0.80.2`（`Dockerfile.test`、`docker/Dockerfile.attempt-pi`、`docker/Dockerfile.runtime`），而这个版本正是落后上游 8 个 minor 版本、即将被上游 npm 包取代的那一份。保留它们等于把「已判定淘汰」的东西又维护一套。
  - Docker attempt 镜像与 egress proxy 服务的是**执行器沙盒兼容路径**（每个子任务跑一个一次性容器）。这条路径本来就是兼容路径而非主路径，且随执行器收敛为 Pi Agent 后失去意义。
  - 维护成本高：镜像里的版本、配置、脚本与主代码不同步，每次产品变更都要额外同步一遍，且没人能保证同步到了。
- 验收：仓库中不存在任何 Dockerfile、镜像构建脚本、Docker 执行后端或 Docker 相关测试。

**FR-CL4.2 云端部署环境形态后续单独决定**
- 产品目标仍是「Server 部署在云端」（FR-S3.1），但**用什么形态承载云端环境，本次不决定**。
- 后续把 Server 打包到云端时**有可能使用 Docker**，也可能用其他方式；到那时再定。
- 原因：现在讨论形态会过早锁死实现，而云端形态的选择依赖届时的基础设施条件（编排平台、镜像仓库、弹性策略、每用户沙盒的隔离方式）。先把产品形态定清楚，部署形态服从它。
- 验收：本次交付不包含任何云端部署制品；但产品在设计上不排斥任何一种形态 —— 云端环境的隔离、规格分配、升级发布三项需求被明确表述（FR-S3.5、FR-S3.6、FR-S1.1），但不被绑定到具体实现。

**FR-CL4.3 隔离职责归属云端环境，而非任务容器**
- 执行只在**原生模式**下运行（子任务进程直接跑在受控的工作区 / 沙盒目录中），不存在「每个子任务一个容器」的路径。
- 原因：
  - 云端形态下，隔离由**云端环境**（每个用户一个沙盒）统一提供，任务粒度再套一层容器是语义重复；
  - 「云端沙盒 + 任务容器」两层隔离叠加，让故障排查变困难；
  - 少一层意味着少一套镜像、少一套对账逻辑、少一处权限面。
- 验收：执行链路只有原生一种；隔离职责单一归属云端环境。

**FR-CL4.4 测试不依赖 Docker**
- 全量测试（尤其 SQLite 与 POSIX 路径用例）不再依赖 Docker 镜像运行。
- 原因：Docker 镜像存在的历史原因之一是本地环境编译不了 `better-sqlite3`。随着 Windows 路径删除、只保留 macOS 与 Linux 开发环境，这个限制不再成立 —— 两者都能直接构建原生依赖。
- 验收：完整测试套件可在 macOS 与 Linux 开发机直接运行通过。


## 3. 产品定位

### 3.1 我们是什么

MetaWork 是一个**部署在云端的个人 Agent 工作台**：

- 用户在任何设备上打开 Web、桌面端或飞书，就能发起一个真实的工作任务（研究、写代码、生成报告、操作工作区文件、跑测试、交付产物）。
- 任务在**云端沙盒环境**里执行，7×24 在线，不依赖用户电脑开着。
- 系统记住用户的偏好、习惯与历史决策，越用越贴合。
- 用量清晰可见，免费额度用得明白。

### 3.2 我们不是什么

- **不是通用办公套件。** 不与 WorkBuddy、豆包等办公产品正面竞争，不做表格、文档协同、IM 这些通用办公能力。
- **不是一个 Agent 框架的转售。** 用户买的是「能完成工作」的结果，不是 Harness、模型或配置的组合权。
- **不是一个按 token 计价的 API 客户端。** 产品不展示、不统计模型原始价格。

### 3.3 目标用户

| 用户 | 场景 | 核心诉求 |
| --- | --- | --- |
| **有具体工程/研究任务的知识工作者** | 丢一个需求进来，产出一份报告、一批代码修改、一份调研 | 任务能真的做完、结果可信、过程可查 |
| **需要长期助理的人** | 每天交代若干件事，希望有人记住偏好、持续跟进 | 记忆可靠、任务不丢、随时能查进度 |
| **想用上自己模型 Key 的人** | 已有 DeepSeek / OpenAI / Anthropic 等账号 | 能用自己的 Key，不被平台额度限制 |
| **想先免费试试的人** | 不确定要不要付费 | 免费额度足够跑几个真任务 |

### 3.4 一句话价值主张

> **把一件要做的事交给 MetaWork，它在云端把它做完，并且让你看得清用了多少、还剩多少。**

## 4. 设计原则

这四条原则是所有需求取舍的裁决依据。

| 原则 | 含义 | 推论 |
| --- | --- | --- |
| **大道至简** | 一个概念只有一种实现。能删的都删。 | 同一时刻只有一个客户端形态、一个执行器、一种路由、一种账单 |
| **用户只看到用量，不看到价格** | 模型原始价格是内部信息，不进入用户界面 | 设置里没有价格输入项；账单页只有 token 数 |
| **平台能托管的，不让用户配置** | 用户配 Provider 是为了用，不该被要求懂成本 | 价格、加价率、费率表不暴露；官方额度的兑换率由平台维护 |
| **开源能力不重复造** | 能用上游成熟方案的能力，就不自研 | Manager 跟随开源 Pi Agent 演进，不维护私有分叉 |
| **自带运行时，不吃用户环境** | 产品能力不建立在用户机器的已有环境上 | Pi Agent 随 MetaWork 打包交付，不依赖用户系统安装 |

## 5. 客户端形态

### 5.1 最终只有三个客户端

| 客户端 | 形态 | 定位 |
| --- | --- | --- |
| **Web** | 浏览器访问 | **默认形态**。主力入口，跨平台，覆盖全部能力 |
| **桌面端（DMG）** | macOS Apple Silicon 原生应用 | 本地工作区访问、文件拖拽、通知、系统集成 |
| **飞书** | 企业 IM 内嵌 | 移动端触发、团队场景、结果直达 IM |

### 5.2 需求条目

**FR-C1.1 终端 TUI 形态取消**
- 不再提供终端界面形态。`metawork` 命令默认打开 Web。
- 原因：Web 与桌面端已覆盖其全部能力，四套界面维护成本高、行为不一致，用户实际使用率低。
- 验收：产品中不存在第四个客户端入口；所有终端命令要么打开 Web，要么归入 Server 管理命令。

**FR-C1.2 桌面端只支持 macOS Apple Silicon**
- 只发布 Apple Silicon 的 DMG。不发布 Intel Mac、不发布 Windows、不发布 Linux 桌面端。
- 原因：Intel Mac 与 Windows 桌面端用户占比低，而 Windows 路径的维护成本不成比例；Linux 用户通过 Web 或云端沙盒使用。
- 验收：发布产物只有 `MetaWork-darwin-arm64.dmg`；其他架构的用户被引导到 Web。

**FR-C1.3 Linux 保留**
- **Linux Server 必须保留**，因为云端沙盒就是 Linux 环境。
- Web 服务与云端沙盒全部基于 Linux 交付。

**FR-C1.4 三个客户端能力对等**
- 三个客户端都能：发起任务、看进度与结果、看用量与额度、看记忆、审批权限、读轨迹。
- 验收：任一客户端能完成的任务，其余两个也能完成，不存在「只有桌面端能做」的功能。

## 6. Manager 与 Executor

### 6.0 唯一的 Pi Agent 运行时（贯穿本节的前提）

**FR-RT1.1 规划与执行共用同一个 Pi Agent**
- Manager 与 Executor 使用**同一个** Pi Agent。不是两个不同版本、不是两个不同实现，而是同一份软件、同一个版本。
- 原因：
  - 同一个软件的两个角色，避免「规划能用、执行不能用」这类割裂能力；
  - 单一版本意味着只有一条上游跟踪线、一套验证面、一份升级路径；
  - 用户心智模型简单：MetaWork 里只有一种 Agent。

**FR-RT1.2 这个 Pi Agent 由 MetaWork 随安装打包提供**
- Pi Agent **随 MetaWork 安装一并交付**，是产品的一部分。
- **MetaWork 完全不依赖用户系统里是否安装过 Pi Agent。**
- 原因：**大量用户根本没有安装 Pi Agent。** 如果 MetaWork 依赖用户自备，则这些用户装完 MetaWork 仍然无法使用核心功能 —— 这是不可接受的。用户自装 Pi 是其个人选择，MetaWork 不感知、不依赖、不使用。

**FR-RT1.3 用户系统的 Pi Agent 与 MetaWork 互不相关**
- 用户系统里已安装的 Pi Agent（无论什么版本、什么配置）与 MetaWork 的 Pi Agent **完全隔离**：
  - MetaWork 不读取、不调用、不修改用户系统的 Pi；
  - 用户系统的 Pi 升级或降级，不影响 MetaWork 的行为；
  - 两者不共享配置、凭据、扩展、会话或任何状态。
- 原因：依赖用户环境会让产品的行为不可复现 —— 同一个 MetaWork 版本在不同用户机器上表现不同，缺陷无法定位、支持无法承诺。

**FR-RT1.4 版本由 MetaWork 钉死**
- MetaWork 内置的 Pi Agent 版本由产品自己决定并锁定，随产品发布升级。
- 验收：产品内不存在「用户可覆盖 Pi 版本」的选项。

**FR-RT1.5 用户零前置条件即可用**
- 验收：在**一台从未安装过 Pi Agent 的干净机器**上，安装 MetaWork 后立刻可以发起并完成一个真实任务（规划与执行全链路）。这是发布门槛级的验收项。

### 6.1 Manager：跟随开源 Pi Agent

**FR-P1.1 平台不自建 Agent 内核**
- Manager 的底层能力来自开源的 Pi Agent，平台**不维护私有分叉**。
- 原因：私有分叉会持续落后于开源社区（当前已落后多个版本），用户拿不到上游的新能力，而平台在付出全部维护成本的同时没有任何差异化收益。
- 验收：仓库中不存在平台自有的 Agent 内核副本；上游版本升级可随产品发布同步进行。

**FR-P1.2 平台能力以「附加件」形式提供**
- 平台在开源 Agent 之上叠加自己的能力：规划约束（只读、不越权）、工作图提案提交、权威事实查询。
- 这些以**官方扩展机制**承载，不修改上游内核代码。
- 验收：平台对上游的改动全部位于扩展文件中，不存在对上游内核的私有补丁。

**FR-P1.3 权限限制在平台侧**
- 平台对规划环节的权限限制（只读、禁止直接改文件、禁止直接跑命令、禁止执行外部动作）由平台自己保证，不依赖上游的行为细节。
- 验收：即使上游行为变化，平台的只读边界不被放宽；安全边界在平台侧有独立验证。

**FR-P1.4 规划能力随上游持续增强**
- 上游发布的新模型支持、新工具能力、新推理改进，平台应当在下一次发布中就能用上，而不是等待平台自行实现。
- 验收：产品发布说明中能体现上游能力被吸收的条目。

### 6.2 Executor：只有 Pi Agent 一个

**FR-E1.1 内置执行器收敛为一个**
- 平台只内置一个执行器：Pi Agent。
- 原因：
  - 没有证据表明不同执行器在配置相同模型时有显著差异；
  - 另一个执行器只兼容自家模型系列，缺少更换模型的灵活度；
  - 多执行器意味着多套配置、多套验证面、多套故障模式，对用户没有价值。
- 验收：用户只能选择一个执行器；没有第二个执行器选项。

**FR-E1.2 执行器就是随安装打包的那个 Pi Agent**
- 执行器即 FR-RT1.2 定义的、由 MetaWork 随安装打包提供的 Pi Agent，**不是**用户系统里安装的那个。
- 用户不需要自己去装、不需要自己管版本，也**不需要事先装好 Pi**。
- 验收：全新环境安装后可直接执行任务，无需任何额外安装步骤；产品文档不要求用户先安装任何 Agent。

**FR-E1.3 执行器可通过 RPC 方式被调用**
- 执行器以进程方式被平台调用，非交互、可脚本化。
- 验收：执行器调用链路在任务执行日志中可见、可审计。

**FR-E1.4 保留扩展位**
- 平台保留「接入其他执行器」的结构性位置。将来需要时能快速接入，不必推倒重来。
- 验收：接入新执行器不需要改动任务调度与授权模型。

## 7. 执行链路与角色分工

### 7.1 角色总览

平台只有三个角色，职责边界清晰、互不重叠：

| 角色 | 职责 | 不负责 |
| --- | --- | --- |
| **Manager（大管家）** | 理解用户需求；拆解成任务图（DAG）；汇总各角色产出的结果并汇报给用户；处理权限申请 | **不**做具体子任务；**不**决定子任务派给谁 |
| **Router** | 对每个子任务决定：由哪个 Agent 承接、该 Agent 用哪个模型 | 不拆解任务；不执行任务 |
| **Executor** | 执行具体子任务，产出结果 | 不拆解任务；不决定派发 |

**用户视角的比喻**：Manager 像一个项目管家 —— 他把「要做的事」拆成「谁做什么」，把活派下去，最后把各家的产出拼装成一份完整的交付给用户。他自己不下场干某一个具体活。

### 7.2 链路

```text
用户需求
   ↓
Manager：理解需求 → 拆解成任务图（DAG）
   ↓
Router：对每个子任务判定 → 哪个 Agent + 该 Agent 的哪个模型
   ↓
Executor：执行子任务 → 产出结果
   ↓
（多个子任务完成后）
Manager：汇总各子任务产出 → 拼装 → 汇报给用户
```

### 7.3 需求条目

**FR-X0.1 角色命名**
- 原「Planner」角色**改名为「Manager」**。产品内不再使用「Planner」指代这个角色。
- 原因：
  - 新职责下的它不是「规划器」而是**大管家** —— 统筹、汇总、汇报，不亲自干活。「Planner」这个名字只描述了旧职责中「拆解」的那一半，会持续误导；
  - 「Manager」直接对应「管家」的语义，与 Executor（执行）、Router（路由）形成一组语义清晰的角色名；
  - 用户界面上的角色名会出现在执行过程展示里，名字要能表达真实职责。
- 验收：产品内所有面向用户的角色称呼统一为 Manager / Router / Executor，不出现 Planner。

**FR-X0.2 Manager 不再是「规划器」**
- Manager 的能力边界随 §7.3 一并调整 —— 它是**统筹者**，不是规划工具。
- 原因：名字变了，职责描述也必须跟着变，否则会出现「叫 Manager 但只干规划」的割裂。

**FR-X0.3 改名覆盖到代码与文档**
- 角色改名**贯穿代码、存储、协议与文档**，不是只改界面文案。
- 验收要点：
  - 代码中的角色命名（类型、模块、事件、错误信息）不再使用旧角色名；
  - 存储中的历史字段与事件类型要么同步改名，要么作为一次性迁移的一部分处理；
  - 对外协议（客户端命令、事件投影）中的角色名同步更新，客户端与 Server 版本一致发布；
  - 架构决策记录中涉及该角色的历史决策，更新为当前职责描述，并把被取代的部分标注取代关系。
- 原因：只改界面不改内部，会留下一半新一半旧的词汇，比不改更糟 —— 每个读代码的人都要自己判断「这两个词是不是同一个东西」。

**FR-X1.1 Manager 只负责理解与拆解**
- Manager 的职责边界到「产出任务图」为止。**拆完之后，它不再参与子任务的派发决策。**
- 原因：
  - 拆解与派发是两种不同性质的判断。拆解需要理解用户意图；派发需要逐子任务评估执行者与模型的适配度 —— 前者一次判断全局，后者是 N 次局部判断，混在一起会让 Manager 承担过重的推理负担；
  - 拆解只需要做一次，而派发需要在每个子任务上重做，把两者分开才能各自优化；
  - 分开后，Manager 的输出（任务图）变得稳定且可审阅 —— 用户能看懂「要做哪几件事」，而不需要看懂「为什么派给这个模型」。

**FR-X1.2 拆解结果不含派发建议**
- Manager 产出的任务图只包含：每个子任务要达成什么、依赖关系、验收标准。
- **不包含**「这个子任务建议用哪个 Agent、用哪个模型」。
- 验收：Manager 的产出中不存在任何 Agent 选择或模型选择字段。

**FR-X1.3 Router 逐子任务独立判定**
- 任务图拆解完成后，**每一个子任务独立交给 Router 判定**。
- 每次判定产出两个结论：
  1. **由哪个 Agent 承接**（该 Agent 的能力域是否覆盖这个子任务）；
  2. **该 Agent 用哪个模型**（该模型的能力、上下文窗口、可用性是否适配这个子任务）。
- 原因：子任务之间差异极大 —— 一个「查资料」和一个「改代码并跑测试」需要的 Agent 与模型完全不同。逐个判定才能给出精准匹配；统一分配必然是错的。
- 验收：任务图中每个子任务都有独立且明确的 Agent 与模型判定结果；用户能看到每个子任务实际由谁、用什么模型执行。

**FR-X1.4 Router 由决策模型给出结论**
- 派发判定由一个**决策模型**给出，而不是由用户配置或固定规则表决定。
- 原因：
  - 子任务与 Agent/模型之间的适配度是语义判断，用决策模型才能准确理解「这个子任务到底要什么」；
  - 规则表需要穷举「子任务类型 × Agent 能力」的组合，现实中组合爆炸且维护不起；
  - 决策模型可以读懂任务图、子任务目标、Agent 的能力手册与模型的特性，给出有依据的判断。
- 验收：每次派发判定都产出一条可读的判定理由，说明为什么选这个 Agent 和这个模型。

**FR-X1.5 判定依据可被用户查看**
- 用户能查到每个子任务的派发判定结果与理由。
- 原因：派发决策直接决定结果质量与成本。用户不干预决策，但必须能事后复盘「为什么这一步用了这个模型」。
- 验收：轨迹视图里能看到每个子任务的 Agent 判定与模型判定及理由。

**FR-X1.6 不需要审批环节**
- Router 的判定结果**直接生效**，不再经过一层审批。
- 原因：审批层是对「上游建议 + 下游批准」双阶段结构的补偿。当派发判定已经由一个专职的决策模型一次性给出时，审批只是在重复确认同一个判断，既增加环节又不增加信息。
- 验收：任务从拆解到派发到执行，中间没有额外的等待确认步骤。

**FR-X1.7 任务完成后由 Manager 汇总**
- 所有子任务完成后，**由 Manager 负责把各子任务的产出拼装成一份完整结果**，并向用户汇报。
- 原因：
  - Manager 是唯一理解「用户到底要什么」的角色，只有它知道某份产出在整体答案中处于什么位置；
  - 拼装不是机械拼接 —— 需要判断哪些子任务的产出是主结论、哪些是支撑材料、如何组织才能回答用户最初的问题；
  - 如果让 Executor 各自汇报，用户会拿到一堆碎片，无法拼出完整答案。
- 验收：用户最终收到的是一份针对原始需求的完整回答，而不是子任务结果的罗列；用户不需要自己拼接。

**FR-X1.8 Manager 不执行具体子任务**
- Manager 自己不承接任何子任务。
- 原因：这正是「大管家」的定位 —— 他的价值在于理解与统筹，而不是亲自干活。

**FR-X1.9 权限申请由 Manager 处置**
- 执行过程中出现的权限申请，**由 Manager 直接决定**。
- 判定分三种结果：
  1. **能直接决定** → Manager 直接批准或拒绝，继续执行；
  2. **不能确定** → 向用户发起申请或澄清，拿到答复后继续；
  3. **明确该拒绝** → 直接拒绝，不打扰用户。
- 原因：
  - 权限申请大多是有明确惯例的（「要读这个目录」「要跑一次测试」），由最懂上下文的人（Manager）判断最快；
  - 频繁打断用户询问权限是体验杀手，尤其是长任务；
  - 但当确实超出常规判断范围时，Manager 应该问，而不是猜 —— 猜错的后果由用户承担。
- 验收：常规权限申请不打断用户；越界或不确定的申请能向用户发起询问并拿到答复；用户能区分「Manager 自己决定」与「问过我」。

**FR-X1.10 权限决策有边界**
- Manager 的权限决定受平台的权限边界约束 —— 平台预先定义的硬性红线（如访问平台级凭据、影响其他用户数据）不因 Manager 判断而放行。
- 原因：把权限裁量权交给一个模型，必须有不可逾越的底线，否则一次误判的后果不可控。
- 验收：触及平台红线的权限申请即使由 Manager 判断也不会被放行。

**FR-X1.11 派发失败有明确归属**
- 当 Router 无法为某个子任务找到合适的 Agent/模型时，明确告知用户「这个子任务没有合适的执行者」，而不是静默丢弃或无限重试。
- 原因：任务图里有一步做不成，用户必须知道，否则交付的是一份缺了关键内容的答案。
- 验收：无法派发的子任务在交付结果中被显式标注，缺失原因可查。

### 7.4 各角色能力要求

**FR-X1.13 任务执行期间不得阻塞用户输入**
- 一个任务开始执行后，**不能因为「当前这个任务还没跑完」就把用户的新输入挡在门外**。
- 用户在整个任务执行期间随时可以继续说话、继续提要求、继续补充信息。
- 原因：
  - **这是用户对 Agent 产品的基本预期。** 无论是 CLI 形态的 Agent 还是桌面 Agent，用户在 Agent 干活时插话、追加要求都是常态，不该被挡；
  - 任务可能要跑很久（分钟级到小时级）。这段时间里用户的需求会变、会想到新东西、会发现方向不对。如果必须等任务跑完才能说话，用户要么干等，要么被迫取消任务重来 —— 两种都很糟；
  - 挡住的代价不是「少一个功能」，而是**用户会转而把任务拆小、频繁取消重来**，反而让产品更难用。
- 验收：任务执行期间提交新输入不被拒绝、不要求用户等待；用户的补充能够影响正在执行的工作。

**FR-X1.14 Manager 判断新输入如何作用于当前任务**
- 执行期间用户的新输入，**由 Manager 判断它该怎么作用到当前正在做的任务上**，而不是由用户自己选择方式。
- 至少需要区分两类语义（用户不必知道这两个词）：
  - **改变方向** —— 用户指出当前做法不对、要求换一种做法。这类输入应当**改变正在执行的工作走向**；
  - **追加范围** —— 用户在当前目标之外又提了新的事情。这类输入应当**作为后续工作追加**，不打断当前正在做的事。
- 原因：
  - 用户说的话是「需求」，不是「操作指令」。要求用户自己判断「这算不算打断」是把实现细节推给用户；
  - 只有 Manager 同时理解「用户说了什么」和「当前任务做到哪了」，所以只有它能做出正确判断；
  - 两类输入处理错了后果不同：该改方向的当成追加 → 用户在等一个错的结果；该追加的当成改方向 → 打断了一件本来快做完的事。
- 验收：任务执行期间用户提出方向性调整，后续工作按新方向走；用户追加新事项，当前工作不被打断且新事项被纳入。

**FR-X1.15 Manager 要告知用户它怎么处理了**
- Manager 处理完执行期输入后，**要让用户知道这条输入被怎么对待了**。
- 原因：用户说了话却不知道有没有被听进去，会产生「我是不是白说了」的不确定感；尤其在任务还在跑、结果还没出来的时候。
- 验收：用户能区分「这条被当成方向调整了」和「这条被排进后续了」。

**FR-X1.16 执行期输入不要求用户重复确认**
- 用户表达完需求即可，不需要为「要插话还是追加」再做一次选择或确认。
- 原因：多一次确认就多一次打断，而用户本来就是为了不被打断才在这里说话。
- 验收：执行期输入提交后直接生效，不出现「请选择处理方式」这类询问。

**FR-X1.17 界面上的角色名与执行链路展示**
- 用户界面上的角色名统一为 **Manager / Router / Executor**。
- 执行过程展示（如轨迹视图）呈现的是**三段式链路**：Manager 拆解 → Router 派发 → Executor 执行。
- 原因：
  - 用户需要看懂「我的任务现在到哪一步了、卡在谁那里」，三个角色名就是这套语言；
  - 旧的三段式是「Planner → Kernel → Executor」，而审批层已被去掉 —— 展示不改会与实际链路不符。
- 验收：界面上的链路展示与 §7.2 的实际链路一致；不出现已被移除的角色名。

**FR-X2.1 Manager 需要的能力**
- 理解用户意图并拆解成任务图；
- 汇总子任务产出并组织成完整答案；
- 处置权限申请（自主决定或向用户询问）；
- 读懂 Agent 能力手册与模型特性，以便做派发判定与汇总（**注**：这是理解，不是决定 —— 决定权在 Router）。

**FR-X2.2 Router 需要的能力**
- 读懂每个子任务的目标与验收标准；
- 读懂可用 Agent 的能力域与可用模型的特性；
- 为每个子任务给出 Agent + 模型的判定与理由。

**FR-X2.3 Executor 需要的能力**
- 在被授权的边界内完成子任务并产出可验收的结果；
- 无法完成时给出结构化的失败原因，供上层判断。

## 8. Router（智能路由层）

**FR-R0.1 角色命名**
- 原「智能路由」层在产品内的角色名统一为 **Router**，与 Manager、Executor 并列。
- 原因：三个角色在用户界面上会并列出现（执行过程展示、轨迹视图），需要有等粒度的角色名。
- 验收：产品内不出现「智能路由」与「Router」混用。

**FR-R1.1 只有一种路由方式**
- 不再让用户选择「成本优先 / 质量优先 / 速度优先 / 均衡」。
- 原因：对普通用户这是伪选择——他们无法判断哪个更好，且平台的定价模型已被移除，「成本优先」甚至失去了含义。
- 验收：设置与执行器配置界面中不存在路由偏好选项。

**FR-R1.2 路由是确定性的**
- 同样的候选模型集合与同样的任务条件，必须得出同样的选择。
- 验收：可复现性有明确验证；不出现「这次选了 A、下次同样情况选了 B」。

**FR-R1.2b 路由是执行链路中的一层，不是用户面对的选择**
- Router 是平台内部的执行环节（见 §7），用户不直接操作它，只在轨迹里查看它的判定结果。
- 原因：路由是「让任务跑对」的手段，不是用户需要理解的概念。把选择权交给用户既无必要也徒增负担。
- 验收：用户界面中没有路由配置入口；路由判定结果只在轨迹中作为可查事实出现。

**FR-R1.3 硬性资格过滤优先于任何偏好**
- 模型是否可用，先由硬条件决定（能力是否匹配、上下文窗口是否够、Provider 绑定是否有效），再在合格者中做确定性选择。
- 验收：不合格的模型无论如何都不会被选中；用户能看到被排除的原因。

**FR-R1.4 兜底顺序清晰**
- 当首选模型不可用时，按用户可见、固定的顺序降级，用户能看到当前实际用的是哪个模型。
- 验收：兜底顺序在界面可见；实际使用模型与界面显示一致。

## 9. 记忆系统

**FR-M1.1 记忆内容独立成 Tab**
- 记忆内容从「设置」里迁出，成为与「对话 / 轨迹 / 账单」并列的独立 Tab。
- 原因：
  - 记忆是产品的核心资产，不是设置项；
  - 记忆数量会持续增长，平铺在设置页里会把设置页撑得无限长，交互极差；
  - 用户需要「翻阅自己的记忆」这个动作，而不是「在设置里找记忆」。
- 验收：Tab 栏出现「记忆」；设置页内只保留记忆的服务配置与开关。

**FR-M1.2 记忆列表必须分页**
- 记忆列表按页展示，不一次性平铺。
- 验收：记忆条目超过一页阈值后出现分页控件；翻页流畅。

**FR-M1.3 记忆可检索与筛选**
- 支持按关键词检索、按记忆类型（偏好 / 人物背景 / 事件记录 / 知识 / 做事方法）筛选、按启用状态筛选。
- 验收：筛选与检索结果正确，翻页与筛选条件正确组合。

**FR-M1.4 记忆可查看完整内容**
- 用户能查看单条记忆的完整正文，不只是摘要。

**FR-M1.5 记忆包可导出**
- 用户能把自己的全部记忆导出为一个**记忆包**，作为个人资产持有、备份或迁移。
- 原因：记忆是用户投入产生的数据，不能被平台单方面绑定。
- 验收：导出产生一个完整、可独立打开的产物；内容覆盖全部记忆条目。
- 待定：导出格式与范围（是否含来源信息、是否含分层结构、是否含检索索引）。

**FR-M1.6 记忆归用户所有**
- 记忆只属于用户账号，平台不将记忆用于跨用户复用。

## 10. 用量统计与账单页

这是本次讨论中变化最大的部分。

### 10.1 从「按任务计费」改为「按时间看用量」

**FR-B1.1 不按单个任务出账单**
- 平台不再为每一个任务单独生成账单，也不展示单笔任务的费用。
- 原因：用户不关心某一次对话花了多少钱；逐笔出单既无业务意义（不卖 token），又制造了大量无意义的状态（已计费 / 待确认 / 无费用）。

**FR-B1.2 不存在「待确认」这类中间态**
- 用量事实要么有，要么没有。不再有一笔费用悬而未决、也不再有「费用暂时无法确认」的提示。
- 原因：「待确认」是金额计费模型的产物。去掉金额模型后，这个状态没有存在理由，只会制造用户的困惑。

**FR-B1.3 所有信息集中在「账单」Tab**
- 账单 Tab 是用量的唯一入口，不再散落在对话卡片、轨迹详情等位置。
- 验收：对话中不再出现金额卡片；账单 Tab 呈现完整用量视图。

**FR-B1.4 以时间为粒度汇总**
- 用量按时间维度聚合展示，粒度支持：**一天、一周、一个月、订阅周期**。
- 原因：时间线才能看出趋势、看出额度消耗速度、看出某天是否异常。
- 验收：可查看今日、本周、本月、本订阅周期的用量。

**FR-B1.5 底层仍可逐条记账**
- 平台内部仍然逐条记录每一次用量（每次模型调用的输入/输出 token 等），只是在展示层做聚合。
- 原因：逐条是准确的事实来源，聚合只是视图。只做聚合会丢失精度，只做逐条无法呈现趋势。
- 验收：聚合结果可回溯到具体记录。

**FR-B1.6 时区固定为北京时间**
- 所有时间聚合以北京时间（UTC+8）为准。
- 验收：跨零点的用量正确落在北京时间的日期里。

### 10.2 页面形态

参照 Cursor 的用量面板，账单 Tab 呈现为：

**FR-B2.1 区间选择**
- 顶部提供时间区间选择器，以及快捷区间（今天 / 近 7 天 / 近 30 天 / 本月 / 上月）。

**FR-B2.2 三张概览卡**
- `Total tokens`：区间内总 token 量。
- `Included`：由 MetaWork 官方额度承担的部分。
- `On-demand`：由用户自己的 Provider 承担的部分。

**FR-B2.3 按天堆叠柱状图**
- 主体图表按天展示，每一天一根柱，柱内按模型分段堆叠，不同模型用不同颜色。
- 原因：堆叠柱能同时看出「总量趋势」和「构成变化」，是这类面板最有效的形态。
- 验收：与 Cursor 面板的视觉与交互一致。

**FR-B2.4 模型图例**
- 图表下方列出涉及的模型（图例），支持点击隐藏/显示单个模型。
- 验收：点击图例后该系列在图中隐藏或恢复。

**FR-B2.5 按 Provider 维度可切换**
- 图表提供「Group By」切换，可在「按模型」与「按 Provider」之间切换。
- 验收：切换后图表与图例同步变化。

### 10.3 统计口径

**FR-B3.1 按 Provider 统计**
- 统计必须能按 Provider 归集，因为「谁的额度」决定了「算不算平台赠送」。

**FR-B3.2 区分「平台额度」与「用户自备」**
- 平台赠送额度内消耗的模型调用，归入 `Included`。
- 用户使用自己 Provider（自己付费）产生的消耗，归入 `On-demand`。
- 平台内部开销不进入用户视野。
- 原因：这是免费额度控制的基础，也是用户理解账单的钥匙。

**FR-B3.3 统计不同模型的用量**
- 按模型分别统计 token 量，用于图表与图例。

**FR-B3.4 用户自带 Provider 的量不占用平台额度**
- 用户用自己的 Key 时，平台不因该用量扣减用户的免费额度，也不限制其用量。
- 原因：用户已经自付费，平台不应重复收费或限流。

**FR-B3.5 平台所有功能都计入用量**
- 平台提供的每一项消耗模型能力的功能，都纳入用量统计。
- 原因：免费额度是平台赠送的有限资源，不统计就无法控制。

**FR-B3.6 不统计价格**
- 平台不计算、不存储、不展示模型原始价格、加价率、金额。
- 验收：设置页无价格输入项；账单页无金额；仓库内无价格字段。

## 11. 免费额度与导流

### 11.1 额度的目的是控制成本

**FR-Q1.1 统计用量是为了卡免费额度**
- 用量统计不是装饰性数据，它是平台控制免费额度成本的手段。
- 验收：额度用尽时，平台确实能据此改变行为。

**FR-Q1.2 额度按周期计算**
- 免费额度按周期授予，周期粒度与用量展示一致：**一天、一周、一个月、订阅周期**。
- 原因：展示与判定用同一时间轴，用户看到的和平台判定的一致，不会出现「显示按天、额度按月」的对不齐。

**FR-Q1.3 额度用尽不硬阻断，而是引导**
- 额度用尽时，平台**不拒绝**用户的新任务，而是提示用户可以转向平台导流的第三方模型供应商。
- 原因：
  - 硬阻断会让用户在关键时刻被卡住，体验极差，且容易引发「凭什么不让我用」的投诉；
  - 导流既解决了用户的即时需求，又为平台带来商业价值 —— 这是同一件事的两面。

**FR-Q1.4 导流供应商目录**
- 平台维护一份可导流的第三方模型供应商目录：供应商名称、可用模型、能力范围、跳转入口、优惠说明。
- 验收：额度用尽时，界面能给出具体的、可点击的替代方案，而不是一句「额度已用完」。

**FR-Q1.5 额度信息对用户透明**
- 用户随时能看到：当前周期的额度上限、已用、剩余。
- 验收：剩余额度在账单 Tab 与额度用尽提示中都能看到。

### 11.2 官方赠送 Provider

**FR-Q2.1 平台提供官方模型额度**
- 平台向用户提供官方托管的模型服务（当前主要接 DeepSeek API），用户无需自备 Key 即可使用。
- 原因：这是「免费额度」这一产品概念的物质基础 —— 没有平台托管的模型，就没有可赠送的额度。

**FR-Q2.2 用户看不到官方 Provider 的 Key 等敏感信息**
- 官方 Provider 的 API Key、平台账号、底层地址、成本信息等，用户一律不可见、不可读、不可导出。
- 原因：这是平台的资产与商业机密，泄露即等于额度被盗刷。
- 验收：客户端拿不到官方 Key；配置界面不暴露官方 Provider 的敏感字段。

**FR-Q2.3 官方 Provider 本身对用户可见**
- 用户能看到「平台赠送额度」这件事存在、当前用了哪个官方模型，但不涉及敏感信息。

**FR-Q2.4 用户自备 Provider 与官方 Provider 并存**
- 用户可以随时添加自己的 Provider，使用自己的 Key；这部分用量走 `On-demand`，不受额度约束。

## 12. 套餐与云端环境

### 12.1 套餐包含两件事

**FR-S1.1 套餐 = Token 额度 + 云端环境规格**
- 用户购买的套餐包含两项核心内容：
  1. **Token 额度** —— 周期内可用的额度量，分包月 / 包年，不同档位不同；
  2. **云端虚拟环境性能** —— 不同档位分配不同的云端算力规格。
- 原因：只有额度没有环境规格，用户拿到的仍是一台弱机器；只有环境没有额度，用户用不起。两项一起才是「一个能用的工作台」。

**FR-S1.2 额度与环境的档位对应**
- 档位越高，额度越多、环境越强。
- **档位数值待定**，后续单独讨论；本次只预留位置。

### 12.2 免费额度

**FR-S2.1 存在免费档**
- 平台提供免费使用额度，让用户先跑通真实任务再决定付费。
- 原因：获客成本低，且免费额度本身有盈利空间（额度对应的模型成本接近于零）。

**FR-S2.2 免费额度按档位差异化**
- 不同付费档位对应的免费额度不同。
- 验收：不同档位的免费额度不同，且随档位递增。

**FR-S2.3 免费额度以相对倍数表述**
- 面向用户不直接给出绝对额度数值，只给出「相当于基准的多少倍」。
- 原因：绝对数值会锚定用户预期并引发比价；倍数表述给产品保留调整空间。
- 待定：「基准」如何定义与对外表述。

### 12.3 云端环境

**FR-S3.1 Server 部署在云端**
- 平台的 Server 运行在云端 Docker / 沙盒环境中，不部署在用户本机。
- 原因：
  - 7×24 在线，用户不要求自己的电脑一直开着；
  - 云端沙盒规格可按套餐弹性分配；
  - 用户本机只做客户端，安装与升级成本大幅降低。

**FR-S3.2 Linux 是唯一的服务端环境**
- 云端沙盒统一为 Linux 环境，平台的安装、升级、运维流程只维护一套。
- 验收：不存在 Windows 服务端路径。

**FR-S3.3 本机部署作为备选形态保留**
- 用户仍可把 Server 装在自己的机器上（含 Apple Silicon Mac、Intel Mac、Linux），走 B/S 架构访问。
- 原因：部分用户对「任务在自己机器上跑」有明确偏好；这也是与通用办公产品区隔的定位点。

**FR-S3.4 特定系统可直接打包为应用**
- 针对 macOS Apple Silicon 等系统，可以直接提供打包好的应用形态。
- 验收：Apple Silicon 用户可直接下载使用，无需自行配置。

**FR-S3.5 云端沙盒承担全部隔离职责**
- 隔离由**云端沙盒环境**（每个用户一个沙盒）统一提供。任务在沙盒内以原生方式执行，不在任务粒度再套一层容器。
- 原因：
  - 「云端沙盒 + 任务容器」两层隔离叠加，语义重复且让故障排查变困难；
  - 云端沙盒已经是用户级的隔离边界，足以覆盖任务级容器原本提供的作用；
  - 少一层意味着少一套镜像、少一套对账逻辑、少一处权限面。
- 验收：执行链路只有原生一种；隔离职责单一归属云端沙盒。

**FR-S3.6 云端环境的形态后续决定**
- 云端环境用什么形态承载（容器、镜像、编排平台或其他）**本次不决定**，等真正要打包上云时再定（见 FR-CL4.2）。
- 但三项需求已经明确，不受形态选择影响：
  1. **隔离** —— 每个用户的环境彼此隔离（FR-S3.5）；
  2. **规格** —— 不同套餐档位分配不同算力规格（FR-S1.1）；
  3. **升级** —— Server 能独立升级，用户客户端不受影响（FR-S3.1）。
- 原因：把形态写死会过早锁死实现；把需求写清则任何形态都能满足。
- 验收：产品设计不绑定任何具体部署形态；上述三项需求在需求层面可被验证。

### 12.4 Server 的网络可达性

**FR-S4.1 Server 不再只监听回环地址**
- Server 必须能监听**任意可配置的网络地址**，而不是写死 `127.0.0.1`。
- 至少支持三种典型取值：
  - `127.0.0.1` —— 仅本机可访问（当前本机部署形态）；
  - `0.0.0.0`（或 `::`）—— 监听全部网卡，服务于云端环境；
  - **指定的具体 IP** —— 例如云主机内网 IP 或负载均衡后的 VIP。
- 原因：
  - **这是云端部署的直接前提。** 云端 Server 必须能被外部客户端访问，写死回环地址等于云端不可用；
  - 云端环境的具体 IP 由基础设施决定（可能是内网 IP、可能是 SLB VIP、可能是 Pod IP），产品不能假设自己知道；
  - 本机形态与云端形态共用一套 Server 代码，差异只应体现在配置上。
- 验收：配置不同的监听地址时，Server 都能正常启动并按预期可达。

**FR-S4.2 对外可达时访问控制仍然生效**
- Server 监听非回环地址时，**认证与授权不得因此放宽**。
- 原因：把服务暴露到网络上会引入真实的安全面。监听地址与访问控制是两件事：前者决定「谁能连上」，后者决定「连上后能做什么」。放开监听地址的同时放开认证，等于把服务裸奔在公网。
- 验收：在监听非回环地址时，未认证请求仍被拒绝；跨来源的连接不被默认放行。

**FR-S4.3 客户端获取 Server 地址的方式可配置**
- 客户端需要知道 Server 在哪里。地址来源不能写死为回环地址。
- 至少支持：配置项显式指定、启动参数传入、以及从 Server 提供的端点信息中读取。
- 原因：云端客户端（Web 天然同源、桌面端、飞书）拿到 Server 地址的途径与本机形态不同 —— 本机是同机回环，云端是公网域名或内网地址。
- 验收：客户端能连上非回环地址上的 Server；本机形态的连接方式不受影响。

**FR-S4.4 跨来源访问的允许范围可配置**
- Web 端与 Server 分离部署时，跨来源访问是常态。哪些来源被允许，需要可配置而非写死为回环地址。
- 原因：现有实现把允许的来源写死为回环主机名，云端 Web（不同域名）会被直接拒绝。
- 验收：配置允许的来源后，Web 端能正常连接；未在允许列表内的来源仍被拒绝。

**FR-S4.5 内部组件仍用回环地址**
- 平台内部组件之间的通信（记忆引擎、内部工具服务、受管本地服务）**继续使用回环地址**，不随 Server 的对外监听地址改变。
- 原因：内部组件与 Server 同进程同主机，没有理由走网络；保持回环能避免它们被意外暴露，也避免在受管本地服务里暴露端口。
- 验收：Server 监听非回环地址时，内部组件仍通过回环通信，且不出现在对外可达的端口上。

## 13. 商业规则

**FR-BIZ1.1 用户买的不只是 Harness**
- 用户购买的是「能完成工作」的结果与配套的额度、环境，不是工具组合权。
- 原因：如果用户买到的只是 Harness，他们随时可以换用别的平台。

- 验收：自带 Provider 的用户在付费与免费状态下都能正常使用。

**FR-BIZ1.3 第三方平台导流位**
- 在用户开通页面与账单页面设置第三方平台导流位，平台与第三方谈成折扣后投放。
- 验收：开通页与账单页存在导流入口；导流内容可配置。

**FR-BIZ1.4 导流与额度用尽提示共用同一目录**
- 开通页、账单页、额度用尽提示三处的导流内容来自同一份供应商目录，避免口径不一。

| 不做 | 原因 |

| **为「以防万一」保留的代码** | 产品未发布，保留只会持续干扰后续判断 |
| **仅为兼容历史数据而存在的分支** | 没有兼容对象；每段兼容代码都是一条需永久维护的分支 |
| **清扫阶段引入新抽象/新功能** | 清扫与建设混在一起会导致「删了什么」无法追溯 |
| **任务粒度的容器隔离** | 隔离由云端环境统一提供；两层叠加语义重复、排查困难 |
| **现存的 Docker 资产** | 镜像里固化的是即将淘汰的 Pi 0.80.2 与已删除的执行器；云端形态后续再定 |
| **写死回环地址的 Server 绑定** | 云端部署的直接前提；监听地址必须可配置 |
| **「Planner」这个角色名** | 新职责下它是统筹与汇总的大管家；界面统一用 Manager |
| **任务执行期间阻塞用户输入** | 与 Agent 产品的基本预期相悖；会让用户被迫取消重来 |
| **让用户自己选「插话还是追加」** | 用户说的是需求不是操作指令；判断是 Manager 的职责 |

## 15. 关键用户旅程

### 旅程 A：首次使用（免费）

```
注册 → 开通（看到免费额度说明与套餐档位）
     → 平台自动配置官方 Provider（用户看不到 Key）
     → 进入 Web（默认）
     → 提一个真实任务
     → 任务在云端沙盒执行，进度可见
     → 交付结果
     → 打开「账单」Tab：今日用量、Included / On-demand、按天柱状图
     → 打开「记忆」Tab：系统已记录本次交互中形成的偏好
```

> 前提：用户机器上**没有安装任何 Agent**。MetaWork 自带的 Pi Agent 已足够完成上面全部步骤。

### 旅程 B：额度用尽

```
任务进行中，额度耗尽
  → 不阻断任务
  → 提示：额度已用完，可转向以下模型供应商（可点击跳转，带优惠说明）
  → 用户选择：自行购买第三方 / 等下个周期 / 使用自备 Key
  → 自备 Key 后继续执行，后续用量计入 On-demand，不占额度
```

### 旅程 C：老用户长期使用

```
每天用 Web 或飞书交代任务
  → 任务在云端持续跑（不要求电脑开机）
  → 「轨迹」Tab 复盘过程与执行细节
  → 「记忆」Tab 看到系统积累的偏好、做事方法、人物背景
  → 导出记忆包作为个人资产备份
  → 「账单」Tab 看本月用量趋势，判断是否需要升级套餐档位
```

### 旅程 D：一个复杂任务的全过程

```
用户：「帮我调研 X 方案，并基于调研结果写一份实现方案」
  → Manager 拆解成三个子任务：
      ① 调研 X 方案
      ② 设计实现架构（依赖 ①）
      ③ 写出方案文档（依赖 ②）
  → Router 逐个判定：
      ① → 研究类 Agent + 擅长长文档的模型
      ② → 架构类 Agent + 强推理模型
      ③ → 写作类 Agent + 通用模型
  → Executor 依次执行，Manager 不下场
  → 中途遇到权限申请（要读某个外部目录）
      → Manager 判断：常规目录读取 → 直接批准，继续
  → 三个子任务完成
  → Manager 汇总：把调研结论 + 架构设计 + 方案文档拼装成一份完整回答
  → 用户收到的是一份可直接用的方案，而不是三份碎片
```

> 用户全程只提了一次需求，没有被问「派给谁」「用哪个模型」，也没有被打断问权限。

## 18. 决策记录

本次讨论中已确认的决策，按主题归并，便于回溯。

### 项目体检与大扫除
- **这是第 1 步，也是所有后续改造的前提** —— 不清扫就改造。
- 当前项目因多轮升级累积了大量冗余逻辑、代码与设计文档，**对后续优化升级产生严重干扰**。
- 需要做一次**全项目体检 + 大扫除**：垃圾逻辑、不必要的逻辑，通通干掉。
- 判定用三个维度：**是否在用 / 是否现役 / 是否唯一**。测试引用不算「在用」。
- 判定为冗余的一律删除，**不保留「以防万一」**。
- 兼容层（历史数据、历史配置、旧协议）随对应产品形态一起清退。
- 文档与代码同等对待：已完成的计划归档、已被取代的决策归档、无效的删除。
- 先出**体检报告**再删；删除**分批推进**，每批可独立验证与回滚。
- 清扫阶段**不引入新功能/新抽象**，只做删除与语义等价重命名。
- 清扫与产品改造**共用一份实施顺序**，不拆成两个阶段。

### Docker 的处置
- **现存 Docker 资产全部删除**：`docker/` 整个目录、根级 `Dockerfile.test`、`official-server/Dockerfile(.test)`、`planner/AnyFusion-Pi/Dockerfile.test`、`tests/docker/` 两个测试、镜像构建脚本，以及代码里的 Docker 执行后端（`docker-cli-attempt-execution-backend.ts`、`container-compatibility-adapter.ts`、`container-cli` 驱动、`docker_socket` 权限项、Docker 标签对账逻辑）。
- 关键理由：**镜像里固化的是即将被淘汰的东西** —— 三处镜像各自装着 `@earendil-works/pi-coding-agent@0.80.2`，正是落后上游 8 个 minor 版本、将被上游 npm 包取代的那一份。保留它们等于把「已判定淘汰」的东西又维护一套。
- **云端部署环境形态后续单独决定** —— 目标是「Server 上云」，但用不用 Docker、怎么部署，到真正打包时再定。本次不产出任何部署制品，但把云端的三项需求（隔离 / 规格 / 独立升级）写清，不绑定形态。
- **隔离职责单一归属云端环境**：不再在任务粒度套容器。
- **测试不再依赖 Docker**：随着 Windows 路径删除、只保留 macOS 与 Linux 开发环境，`better-sqlite3` 的编译限制不再成立。

### 客户端
- 终端 TUI 取消；只保留 Web、桌面端、飞书。
- 裸命令默认 Web。
- 桌面端只支持 macOS Apple Silicon；Windows 停掉；Linux 保留（云端沙盒是 Linux）。
- 客户端能力对等。

### Manager / Executor
- Manager 与 Executor **共用同一个** Pi Agent（同一版本）。
- 这个 Pi Agent **由 MetaWork 随安装打包提供**；**MetaWork 不依赖用户系统是否安装了 Pi Agent**；用户系统的 Pi 与 MetaWork 内置的 Pi 完全隔离，MetaWork 不读取、不调用、不使用、不修改它。
- Manager 改用开源 Pi Agent，平台不再维护私有内核；平台能力以官方扩展机制叠加；权限限制在平台侧保证。
- 内置执行器只保留 Pi Agent 一个；保留接入其他执行器的扩展位。
- MCP 能力、RPC 安全策略采用 Pi Agent 自带的。

### Server 的网络可达性
- **Server 的监听地址必须可配置，不能写死 `127.0.0.1`** —— 至少支持回环地址、全网卡（`0.0.0.0`）、指定具体 IP。
- 这是**云端部署的直接前提**：云端 Server 必须能被外部客户端访问，且云端的具体 IP 由基础设施决定，产品不能假设自己知道。
- **对外可达不等于放开访问控制** —— 监听地址决定「谁能连上」，认证授权决定「连上后能做什么」，两者独立。
- **客户端获取 Server 地址的方式可配置**（显式指定 / 参数传入 / 从端点信息读取），跨来源允许范围也可配置。
- **内部组件继续走回环**，不随 Server 对外监听地址改变。

### 执行链路与角色分工
- **角色改名**：「Planner」改名为 **「Manager」** —— 新职责下它是统筹与汇总的大管家，不是规划器；界面角色名统一为 **Manager / Router / Executor**。
- **三个角色**：Manager（大管家）/ Router（路由）/ Executor。
- **Manager 只做理解与拆解**：产出任务图（DAG）即止，不含任何 Agent/模型选择建议。
- **Router 逐子任务独立判定**：每个子任务单独决定「哪个 Agent 承接」+「该 Agent 的哪个模型」。判定由一个**决策模型**给出。
- **去掉审批环节**：派发判定结果直接生效，不再经过 Kernel 式审批。
- **任务完成后由 Manager 汇总**：把各子任务产出拼装成一份针对原始需求的完整回答，汇报给用户。
- **Manager 不执行具体子任务**，是「不干活、只统筹和汇报」的大管家。
- **权限申请由 Manager 处置**：能判断的直接决定；判断不了的向用户申请或澄清。
- 用户全程只提一次需求，不被打断问「派给谁、用哪个模型」，也不被常规权限申请反复打断。

### 任务执行期的用户介入
- **任务执行期间不阻塞用户输入** —— 不能因为当前任务没跑完就把用户挡在门外；用户可以随时追加内容、提出新要求。
- 判断「这条输入是改变方向还是追加范围」**由 Manager 做**，不由用户选。
- Manager 要**告知用户处理结果**，让用户知道自己的话有没有被听进去。
- 不要求用户为「插话还是追加」二次确认。
- 具体怎么实现（Manager 常驻还是唤醒、是否需要改任务图、要不要停掉在跑的步骤）属于详细设计，本次不决定。

### 计费 / 用量
- 不按任务计费；无「待确认」状态；全部信息在账单 Tab；按时间粒度汇总；底层仍逐条记账。
- 时区固定北京时间。
- 时间桶：一天、一周、一个月、订阅周期。
- 页面形态照 Cursor 用量面板：区间选择 + 快捷区间 + 三卡 + 按天堆叠柱 + 模型图例 + Group By 切换。
- 所有体现模型原始价格的内容全部删除；平台不统计价格。
- 路由不再有偏好目标，统一为 Router。

### 记忆
- 记忆内容独立成 Tab，与对话 / 轨迹 / 账单并列；设置页只留服务配置与开关。
- 列表分页 + 检索筛选；支持导出记忆包。

### 商业
- 套餐 = Token 额度档位 + 云端环境规格档位。
- 免费额度按档位差异化，以相对倍数表述；绝对数值不对外。
- 允许自带 Key；自带 Key 的用量不占额度。
- 额度用尽不阻断，改为提示可导流的第三方模型供应商。
- 开通页与账单页设置第三方导流位。
- 官方赠送 Provider 对用户不可见其 Key 等敏感信息；平台负责对接好 DeepSeek API。
- Server 部署在云端 Docker / 沙盒；本机部署作为备选形态保留。
- 套餐订阅当前是 Demo，后续整体替换，不围绕现状做兼容设计。

### 未决（已确认留给后续）
