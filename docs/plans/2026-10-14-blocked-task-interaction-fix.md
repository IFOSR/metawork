## 根因与范围

Web 使用 `task.canCancel` 判断是否运行；但未完成的阻塞、排队任务仍可取消。
因此执行器已经退出、Task 已阻塞时，Composer 仍显示执行中并禁止发送，用户只能停止任务。
`/task dashboard` 还缺少即时查询准入，查询回复也可能继承其他后台任务的运行标记。

这是状态展示与命令准入问题，不修改上游 Provider、不实现完成认证草案，也不自动重试用户现有任务。

## 实施

1. Web 只消费 Task Domain 已投影的 phase，取消权限不再用作运行事实。
   已关联 Task 的权威阶段覆盖遗留 Turn 的 running 标记；独立 Planner 回合仍保留运行状态。
2. Composer 在运行中也允许发送。查询可即时处理，业务输入仍经过现有邮箱与 Kernel 队列。
   全局停止仅选择正在推进的任务；历史阻塞任务的取消操作保留在任务卡片。
3. 对话中显示阻塞、等待、重试、交付、清理的说明。阻塞卡片提供定向 `/task resume`、
   `/task show` 和 Dashboard 按钮，使用现有 Gateway 命令路径，不直接修改 Task。
   重试请求的受理不等于已成功执行；以会话中的 Kernel 处理结果为准。
4. Dashboard 进入现有即时命令路径，不替换正在执行的回合及取消控制器。
   查询回复独立结束，不继承另一个任务的后台执行标记。

## 所有权与边界

- Task Domain 继续拥有生命周期与 phase；Web 仅据其展示按钮和提示。
- Session 拥有命令邮箱及取消控制器；Gateway 拥有命令回复与准入。
- 保留 ADR-0037：阻塞任务仅在执行、发布、租约和控制操作残留消失后释放会话位置，
  新任务走原队列；显式恢复必须重新获得位置，不因用户提交新指令而偷偷恢复旧任务。
- 无数据库 schema 变更，无第二调度器，无存储绕过；活动摘要增加可选的执行清理显示事实。
- 不改运行中的用户配置，不安装或重启本地服务，不发布 GitHub。
