- 待确认边界：本文第 4 节对排队、暂停、阻塞任务采用更严格的“非空闲”定义
- 实施计划：[执行助手空闲态管理实施计划](2026-09-19-executor-idle-management-implementation-plan.md)

## 1. 先统一几个名称

建议产品讨论和本方案主要使用下面这些名称。代码中的已有名称不因此重命名。

| 我们使用的名称 | 是什么 | 例子 |
| --- | --- | --- |
| 模型 | 理解问题、推理和生成内容的“大脑” | 在模型服务中配置的某个模型 |
| 模型服务 | 提供模型访问地址和密钥的服务 | 配置 API 地址、Key 的地方 |
| 执行工具 | 让模型能够读文件、运行命令、使用工具的软件 | Pi、Codex CLI |
| 执行助手 | 用户配置的一个负责某类工作的助手，对应 Executor 配置 | 研究助手、开发助手 |
| 规划助手 | 理解用户需求，提出由谁做、如何拆分工作的安排 | MetaWork 当前的 Planner |
| 接入程序 | MetaWork 与一种执行工具之间的连接代码 | 代码中的 Driver |
| 启用 / 停用 | 允许 / 不允许后续新工作选择某个执行助手 | 暂时停用研究助手 |
| 热生效 | 不重启 MetaWork，配置保存成功后，下一次工作就使用它 | 新增助手后直接发起新任务 |
| 配置版本 | 系统保存一次配置时留下的内部版本记录 | 代码中的 revision |

它们的关系可以用一个例子说明：

> 你创建一个叫“研究助手”的执行助手，选择让它使用 Pi，再为它选择模型，
> 并说明它适合做资料检索和报告整理。MetaWork 安排工作时选择“研究助手”，
> 底层通过 Pi 的接入程序启动 Pi，由 Pi 使用指定模型完成工作。

执行助手不是模型的另一个名字，也不是必须独立安装的一套软件。
多个执行助手可以共用 Pi，但使用不同模型、职责说明和已有的权限方案。
新增助手不意味着后台立即多启动一个长期运行的进程。

其余技术名词只供阅读代码时对照：

| 代码名称 | 通俗理解 | 用户是否需要直接管理 |
| --- | --- | --- |
| `AgentClass` | 一份助手配置；也用于描述规划助手 | 不直接编辑这种底层对象 |
| `Harness` | 执行工具如何启动的配置 | 本版不开放 |
| `driverId` | 接入程序的真实类型标识 | 本版不开放 |
| `Work Unit` | 某次实际启动出来工作的运行实例 | 不需要 |
| `AccountRuntime` | 同一账户所有会话共用的后台运行服务 | 不需要 |
| `Kernel` | 检查并批准任务执行安排的系统核心 | 不需要 |
| `modelPolicy` | 指定模型，或者允许系统从哪些模型里选 | 通过表单设置 |
| `permissionProfileRef` | 对一个已有权限方案的引用 | 通过中文选项选择 |

“职责说明”帮助规划助手选择合适的人，不会自动安装工具、扩大权限或创造能力。
“允许联网”等选项也不能解释为完备的操作系统隔离保证，仍以现有执行后端的真实边界为准。

## 2. 本版要做什么，不做什么

核心规则：

> 系统有尚未结束的工作时，不允许修改执行助手配置。
> 系统完全空闲时，允许新增、编辑、启用、停用和删除执行助手，成功后立即热生效。

本版交付：

- 设置页面完整管理执行助手。
- 只选择当前已经支持的 Pi 和 Codex CLI。
- 修改名称、模型选择、职责说明、已有权限方案及启用状态。
- 复用相同工具创建多个助手，不复制安装执行工具。
- 忙碌检查覆盖同一账户的所有 Workspace、Conversation 和客户端。
- Web、CLI 和直接管理 API 使用相同的后端限制。
- 修复内部助手名单不刷新、按配置名字猜工具类型的问题。
- 保留 Planner 现有模型配置功能，不增加 Planner 的增删、启停入口。

明确不做：

- 新执行工具、远程执行、A2A、动态插件加载。
- 任意命令、启动参数、镜像、运行目录、接入程序配置。
- 在执行过程中切换配置、等待排空后自动切换、后台预约配置更新。
- 为此次管理功能新增“旧任务继续用旧配置、新任务同时用新配置”的执行机制。
- 新权限规则、任意 Skills/MCP/插件安装管理。
- 重写规划、调度、取消、恢复或任务完成判定。

保留已有配置版本、审计、任务记录和历史显示，不实施版本删除或数据库去版本化。
“不新增多版本并行执行机制”不等于“删除当前系统已有的历史记录和版本约束”。

## 3. 用户最终能怎样操作

### 3.1 新增执行助手

在设置页点击“新增执行助手”，填写：

- 名称，例如“开发助手”。
- 执行工具，从 Pi、Codex CLI 中选择。
- 使用的模型，指定一个模型，或者选择允许系统自动挑选的模型范围。
- 职责说明，例如“优先负责代码修改和测试，不优先承担市场资料检索”。
- 允许的操作范围，从系统提供的既有中文权限选项中选择。
- 是否立即启用，默认启用。

系统自动生成不可变的内部 ID，关联已安装、已配置的工具入口，补齐受控字段。
用户不填写 `harnessRef`、Driver、命令、路径或 `generatedRuntimeRef`。
界面只展示经过后端确认的模型兼容性和能力预览，不让用户勾出并不存在的能力。

工具目录始终只有 Pi、Codex CLI。缺少对应可复用工具配置时，选项显示不可用，
说明需要完成安装/初始化；不在“新增助手”请求中隐式创建或修改底层启动配置。
工具配置存在但本地程序缺失时，可以保存为停用状态；启用必须通过必要检查。

### 3.2 编辑与保存

第一版允许修改名称、模型策略、职责说明、已有权限方案和启用状态。
执行工具在创建后保持不变；想把 Pi 助手改成 Codex 助手，应新增助手再删除旧助手。
这个约束避免“普通编辑”同时承担运行方式迁移。

保存过程是：

```text
确认系统空闲
  -> 检查字段、模型和权限引用
  -> 检查职责说明和能力预览是否有效
  -> 检查需要启用的执行工具
  -> 一次性保存并刷新后台配置
  -> 返回“已生效”
```

能力说明继续使用现有的服务端校验和语义确认流程。修改后的非空说明没有得到有效确认，
不能假装分析成功并激活；清空说明按现有确定性流程处理。
创建助手的说明预览需要接受“候选配置中的新助手”，不能只允许预览当前已存在的助手。

普通用户不操作“保存但暂不生效”。保存成功即热生效，失败就维持原配置。
用户已经填写的本地表单可以在失败后保留，但它不是生效配置或后台待执行的更新。

### 3.3 启用与停用

“启用”表示允许后续新工作选择它，不是马上启动一个常驻进程。
“停用”表示后续新工作不再选择它，不是终止一个正在执行的任务。

本版只在系统空闲时允许操作，因此不会出现“点停用时还有它正在做的工作”。
如果用户想停止正在做的工作，应使用现有任务取消功能，并等待清理完成。

停用助手仍可查看、编辑和删除。启用时重新检查模型、工具和权限。
启用状态、工具是否安装、最近一次执行是否失败，是三种不同信息，界面分开展示。

### 3.4 删除

删除只移除当前配置里的这个助手，不删除 Pi/Codex，不删除共享模型服务、Key、
历史任务、交付产物或历史配置记录。不能级联停用其他共用同一执行工具的助手。

确认文案示例：

> 删除“研究助手”后，后续任务不再使用它。历史工作和文件保留。

允许删除最后一个助手，也允许停用全部助手；系统仍可登录、浏览历史和进入设置。
没有可用助手时，新工作入口明确提示“请先新增或启用一个执行助手”，
不能让 Planner 接到业务请求后才无路可走。这个新工作限制与现有 Pi 安装就绪检查并存，
不能把安装就绪当成执行助手存在，也不能顺带开放 Planner 直接完成业务工作。

内部 ID 不因名称变化而改变。删除后重新创建同名助手，产生新的 ID。
原有 `pi-agent`、`codex-cli` 等兼容标识不重命名；用户可删除其配置，
但 Server 重启不能自动把已删除的内置助手补回来。

### 3.5 忙碌时看到什么

设置可以浏览，但助手新增、编辑、启用、停用、删除和有副作用的测试按钮禁用。
不提供忙时保存草稿到服务端、自动排队更新或“强制保存”选项。

提示示例：

> 当前账户仍有工作在规划、执行或等待继续，暂时不能修改执行助手。
> 请先完成或取消这些工作，待清理结束后重试。

点击提示可查看相关任务及会话；不要只告诉用户一个无法理解的内部错误码。
如果打开表单后其他会话开始工作，表单转为只读，已输入内容可以留在本地。
提交时后端还会重新检查，不依赖按钮是否变灰。

## 4. 什么叫“系统空闲”

### 4.1 已确认的硬规则

正在规划和正在执行都属于忙碌，而且检查范围是整个账户，不是当前页面。
执行结束后的验证、合并发布、取消清理和恢复检查未完成，也不能修改。
仅仅没有新的界面输出，或当前会话没有任务，不代表系统空闲。

### 4.2 为“不维护旧任务的执行配置”提出的必要补充

当前代码允许没有运行进程的 `ready`、`parked`、`blocked` 任务与配置更新共存。
这些任务仍可能恢复并需要原配置。因此，“没有正在执行的进程”
不能单独推出“不再需要旧配置”。

本文建议第一版采用严格规则：

> 排队、暂停、等待用户批准、缺少材料、失败后等待恢复的任务，只要尚可继续，
> 都算未结束工作。先完成或明确取消，才能改执行助手。

这是根据用户“先简单考虑、不做旧配置执行维护”的目标提出的设计选择，
比现有 ADR-0033 更严格，尚需确认。不是声称用户已经逐项确认过这些状态。
如果要求暂停/阻塞任务存在时仍能改配置，就必须重新设计其恢复方式，不能同时保留
“无需处理旧配置”的假设。本文不采用静默重绑最新模型、自动取消任务等替代做法。

| 当前情况 | 是否允许修改 |
| --- | --- |
| 某个会话正在理解需求、规划工作 | 否 |
| 工作在排队，或有已接收但尚未处理的新工作请求 | 否 |
| 正在执行、验证结果、合并发布或取消清理 | 否 |
| 有暂停、阻塞、等待批准或等待恢复的未结束任务 | 否，按本文建议的严格规则 |
| Server 启动恢复或后台恢复尚未结束 | 否 |
| 另一个配置修改/说明分析事务未结束 | 否 |
| 全部任务已结束，且没有待处理工作或清理 | 是 |
| 只有浏览历史、打开设置或空闲连接 | 是 |
| 对话要求澄清，当前轮已结束且没有待继续任务 | 是 |

实现不能只看任务的 `running` 字段：至少覆盖 `created`、`ready`、`running`、
`parked`、`blocked`，以及任务之外的 Planner turn、已接收请求、后台执行和清理事实。
`done`、`archived`、`cancelled` 也只有在相关清理已经完成时才不阻塞。
未知活动状态默认拒绝写入，给出诊断，而不是当作空闲。

### 4.3 避免两边同时开始

要防止这样的顺序：“保存检查时空闲 -> 另一个会话开始规划 -> 配置仍然被改掉”。

因此，开始工作与开始配置修改必须互斥：

- 工作先被接受，修改配置返回忙碌。
- 配置事务先开始，新工作明确返回“配置正在更新，请稍后重试”，不悄悄丢弃或启动。
- 任务取消、只读状态查询、历史查看继续可用。
- 修改事务成功或完整失败后释放限制。
- 有效配置与内存刷新不能恢复一致时，保持禁止新工作的故障状态，不能宣称保存失败后已恢复。

后台定时检查、断线请求重放和恢复工作也必须尊重这个限制。
管理页面产生的说明分析/工具探测是配置事务，不应同时被当成普通业务任务，
否则会出现配置事务阻塞自己的情况。

## 5. 名称不应该影响模型兼容性

执行助手叫“开发助手”“审查助手”，底层工具配置叫任何合法名字，
都不应改变同一种工具可用的模型范围。

系统应沿着配置引用找到真实的 `driverId`，用它判断是 Pi 还是 Codex CLI。
前端只使用服务端输出的兼容性结论，不再单独通过名字猜测。

保留现有业务规则，不在这次改动中扩大支持范围：

- Codex 的 Auto 模型池继续执行当前 GPT-family 筛选规则。
- Pi 的 Auto 模型池继续从当前支持的模型服务目录中选择，再受用户选择和结构能力约束。
- Fixed 模式继续执行既有规则，不借机将 Auto 的限制扩展成新的全局模型政策。
- 本版不新增 Provider 协议；不能因 Schema 接受某种协议，就宣称实际私有绑定已经支持。
- 未知或不受支持的真实工具类型返回不可用，不能猜成 Pi。

## 6. 配置如何热生效

### 6.1 使用已有保存机制，不另建系统

继续通过现有 ConfigurationService 和 AccountRuntime 的激活机制保存配置，
复用校验、编译、探测、版本冲突检查、凭据暂存、失败补偿和客户端通知。
既有历史文件、版本标识和绑定校验保持不变。

第一版无需新增助手数据库表，不把 `agent_classes` 表变成第二套可写配置源。
配置仍是唯一权威来源，运行状态和历史记录仍各自保留。

### 6.2 修复启动时名单不刷新的问题

`AgentClassService` 不能一直持有 Server 启动时的助手集合。
它应通过注入的配置读取接口得到当前已生效的集合；现有明确带版本的执行检查
仍核对授权中指定的版本，不把最新版本当作历史绑定的替代品。

保存成功前，以下消费者必须一致：

- 设置页的助手列表。
- 规划助手可选择的执行助手目录及能力说明。
- 执行前的助手存在性和启用状态检查。
- 执行工具、模型、权限和私有运行环境绑定。
- 就绪状态与界面状态投影。

不因为已有 `AgentClassService` 就额外建一个独立“助手注册表”。
不为了启用助手直接把 Kernel 健康状态写成 `healthy`；配置探测和动态健康仍是不同事实。

### 6.3 只放开明确安全的助手改动

现有代码把整个 AgentClass 的增删判为需要重启。应改为按结构判断：

| 变更 | 本版处理 |
| --- | --- |
| 新增使用既有 Pi/Codex 工具配置的执行助手 | 空闲时热生效 |
| 名称、模型策略、说明、既有权限方案引用、启用状态 | 空闲时热生效 |
| 删除执行助手 | 空闲时热生效 |
| 修改助手的执行工具 | 本版拒绝；改用新增加删除 |
| 改命令、Driver、镜像、启动参数、权限规则定义 | 不纳入普通助手管理 |
| 增删 Planner、修改 Planner 类型 | 本版拒绝 |
| Planner 已有模型配置更新 | 保留已有能力，经同一配置写入保护 |

不能把所有 `agentClasses.*` 路径统一列为热生效。完整配置上传、
回滚和 CLI 同样需要执行结构判断，不能绕过表单限制。

### 6.4 同工具多个助手

两个 Pi 助手可以选择不同模型，两个 Codex 助手也一样。
每次执行仍明确指定授权模型并使用私有运行目录，不能依赖某个叫 `pi-agent`
或 `codex-cli` 的助手提供默认模型。

优先保留现有运行目录协议，以已授权的具体模型和助手设置构造运行输入。
删除内置名字的助手后，其他同工具助手应继续工作；共享工具模板不得包含另一个助手
特有的权限、说明或工具配置。本版不引入第三种接入程序或新的目录协议。

## 7. 写入入口与安全边界

### 7.1 所有入口由 Server 统一判断

Web、CLI、完整配置激活和回滚都调用同一个服务端配置管理入口。
CLI 不得在 Server 旁边另开配置服务、直接切换文件指针。
Server 未启动或无法认证时，CLI 明确报错；本版不提供离线写入回退。

CLI 复用现有 loopback Management HTTP API 与访问 token 鉴权，
从已验证的 Server endpoint 找到地址。token 由操作者显式提供，
不放 URL、命令行参数或日志，不从 endpoint manifest 获取秘密。
本版无需启动另一个管理 Server，也不新增 Executor 传输协议。

安装和升级仍使用现有独占生命周期机制，不借本功能开放运行中直接编辑配置文件。
用户在操作系统层面手工改文件不属于可支持的配置入口。

### 7.2 防止间接修改执行助手

更改共享模型服务、模型、Key，也可能改变执行助手实际使用的条件。
为避免绕过限制，本版建议所有生效配置写入和共享凭据写入统一使用严格空闲门禁，
不先做复杂的“这个字段究竟影响哪个助手”的依赖分析。

这会使 Planner 设置同样受到更严格的未结束任务限制，但不改变其模型选择功能。
凭据状态查询必须只读，不能在忙碌时借读取操作偷偷导入或替换 Key；
自动导入只在受保护的初始化/配置事务中执行。

### 7.3 小接口，不引入新权威

在 ConfigurationService 对外 facade 中新增助手草稿构造操作，服务端补全底层字段。
草稿只是一次请求的候选值，不新增独立、持久、自动排队的草稿仓库。

建议接口：

```text
GET  /api/config/executors
  当前版本、助手列表、Pi/Codex 可选项、是否允许修改及原因

POST /api/config/executors/prepare
  baseRevisionId + create/update/enable/disable/remove + 用户字段
  返回待确认候选配置、变更摘要、能力预览所需数据；不激活

POST /api/config/activate
  复用现有入口，提交候选配置并执行完整原子激活
```

`prepare`、有副作用的说明分析/测试和 `activate` 都必须检查门禁。
`prepare` 返回后不长时间占锁；保存时再次核对空闲状态和原版本号。
两个窗口同时修改时只有一个可以保存，另一个得到“配置已变化，请刷新”。
POST 重试用已有 `baseRevisionId` 冲突检查防止重复生效，不新增数据库请求去重表。

可恢复的常见错误统一映射为中文：

| 错误类别 | 用户提示 |
| --- | --- |
| `runtime_busy` | 系统仍有未结束工作，暂时不能修改 |
| `revision_conflict` | 配置已被其他窗口修改，请刷新 |
| `invalid_configuration` | 指出名称、模型、说明或权限中需要修正的字段 |
| `probe_failed` | 工具不可用或必要检查失败，原配置不变 |
| `unsupported_change` | 本版不支持修改执行工具或底层运行规则 |
| `activation_failed` | 保存未完成；仅在补偿确认成功时说明原配置仍有效 |
| 运行状态无法确认 | 暂停配置修改与新工作，展示恢复诊断 |

## 9. 实施与验收摘要

按下面顺序实施，详细步骤见配套计划：

1. 确认严格空闲边界，并修订 ADR-0033 对暂停/阻塞任务的原规则。
2. 补门禁和竞争测试，再实现账户范围的互斥。
3. 实现 Pi/Codex 助手表单到候选配置的转换与校验。
4. 修复名称推断，并打通列表、能力目录和执行输入刷新。
5. 放开受控的增删改启停热生效，完成失败回滚。
6. 接入 Web 与 CLI，关闭共享凭据和完整配置等旁路。
7. 用真实 Planner/Executor 链路验收，确认 Server PID 不变且新配置确实用于执行。

验收必须包含：

- 规划中、执行中、收尾中、暂停/阻塞时，以及另一个会话忙碌时，五种写操作都被拒绝。
- 保存和新请求同时到达时，只有一方能先进入，另一方得到明确反馈。
- 空闲时新增两名使用同一工具、不同模型的助手，不重启即可被正确选择和执行。
- 任意合法配置标识、任意显示名称，不改变 Pi/Codex 的兼容性结论。
- 停用后新工作不选择它；启用后不再被启动时旧名单拒绝。
- 删除内置名字的助手后，其他助手正常，重启不自动复活已删除配置。
- 零启用助手时可管理设置，但不能接收新的业务工作。
- 保存失败不留下部分配置或新凭据；无法完整补偿时禁止新工作。
- 历史任务、产物、审计仍可查看；不增加跨配置版本继续运行旧任务的承诺。

## 10. 本文与当前实现的关系

本文是待实施方案，不是已交付说明。当前权威代码和已接受 ADR 在实施前继续有效。
严格空闲边界确认后，实施第一步需更新 ADR-0033；工具真实身份投影和助手管理边界
对应修订 ADR-0028，继续服从 ADR-0020、ADR-0027、ADR-0031、ADR-0037。

前次审查发现的历史版本磁盘加载缺口仍是已知问题；本版不宣称已经修复，
也不把它扩展成新的多版本执行项目。对于升级前遗留的跨版本可恢复任务，
保持失败关闭并展示诊断，不能换成最新配置继续；发布前必须检查这类遗留状态，
必要时先在旧环境完成或明确取消，无法清理则阻止该账户进入可写配置状态。

如果不能接受“暂停/阻塞任务也需先结束”的产品限制，应在实现前重新确认范围，
而不是在代码里临时加入历史版本回退、自动重绑或静默取消。
