## 1. 产品决定

取消新增、编辑执行智能体中的“允许的操作范围”下拉框，不再要求用户在“公共网络资料研究”和“工作区开发和文档处理”之间二选一。普通执行智能体默认具备可用工具提供的基础操作，包括公共网络访问、任务文件读写、文档处理和常规工作区命令。

职责负责描述任务范围、目标和分工。例如，研究智能体可以联网查资料、写脚本分析数据并生成报告；开发智能体可以查询公共文档、修改代码并运行测试。不再由“研究型／工程型”预设禁止这些正常组合。

此处的默认开放针对执行智能体。Planner 继续通过既有只读查询与提案工具工作，不因此获得任意文件写入、命令执行或 Executor 控制权；Electron/Web 也不获得直接文件系统、shell 或授权接口。

## 2. 三层契约

| 层次 | 来源与用途 | 禁止的混用 |
| --- | --- | --- |
| 职责与分工 | 用户描述期望任务，由现有 Planner/路由结合模型与工具证据选择智能体 | 不从职责文字生成权限、审批或硬能力声明 |
| 实际能力 | 已安装工具、模型协议与模态、可用连接及运行健康事实 | 默认权限不表示工具已安装、网络必定可达或模型支持任意任务 |
| 操作权限 | 系统维护的基础方案、任务资源边界及具体敏感操作授权 | 不以职责、角色名、AI 改写结果代替授权；不创建第二个语义路由器 |

删除创建模板中由旧权限预设自动附带的“只擅长研究／避免仓库修改”等分工提示。工具实际提供的文件、命令、公共资料能力仍要如实投影；历史兼容字段不得重新成为基于泛化标签的路由门槛。

用户自己填写的职责、适用场景与限制继续作为语义分工依据。迁移只清理能确定来自旧系统模板的提示，不能按关键词删除用户内容。

## 3. 默认操作与边界

| 操作 | 默认行为 |
| --- | --- |
| 访问公开网页、下载公共资料 | 基础操作可用；受支持的受控网络请求自动使用既有规则，不因“研究／开发”标签反复询问 |
| 读写任务工作区、创建报告、处理中间数据 | 基础操作可用，沿用任务资源、输入与产物契约 |
| 运行分析脚本、构建与测试等常规工作区命令 | 对应工具可用时直接执行；命令产生的具体副作用仍受资源及授权边界约束 |
| Provider 模型调用 | 继续由现有模型绑定和凭据注入机制负责；不暴露 SecretStore 原始密钥 |
| 系统设置、凭据访问、对外发送或发布等敏感操作 | 不属于基础默认授权；沿用系统统一的具体请求、Kernel 决策与用户授权流程 |
| 跨账户/跨任务数据、宿主逃逸、控制面资源等禁止目标 | 不因职责或普通审批变为可用 |

“统一授权”只承诺复用已有、已实现的授权能力；当前不支持的外部副作用必须明确返回不支持，不能展示一个实际上无法执行的万能审批按钮。授权范围仍绑定目标、操作、attempt、时效与预算，前端不直接发放权限。

原生 worktree 模式延续现有普通用户文件访问边界，不在此方案中新增整机沙箱，也不承诺所有本地命令都经过细粒度拦截。Docker 模式保持只读输入、工作区写入及公共 HTTP(S) 出口代理；不开放宿主网络、控制 socket、设备或任意内网。两种模式要分别验证，不能用原生成功代替 Docker 出口验证。

## 4. 系统维护的基础方案

新增代码定义的内部 profile `standard-agent`，组合工作区基础操作和归一化的公共 HTTP(S) 目标授权。引用 `standard-agent` 使用空参数；引用 `standard-agent-read-8` 使用同一 profile，并保留旧工程标准方案的 `maxAdditionalReadPartitions: 8`。该标识仅用于配置、绑定、审计和恢复，不作为用户需要选择的业务分类。

不能直接把历史 `workspace-engineering` 的含义改成允许联网，也不能将所有智能体简单改绑到名称和模板仍表示“研究”的旧 profile。旧 profile 与规则身份保持可解释，历史配置和已授权任务继续按固定 revision 解析。

工具、协议、模型模态、资源归属、凭据引用和健康检查仍由各自现有 owner 提供。权限方案不再生成智能体业务能力；对一个工具缺少的能力，系统如实显示限制并由既有路由选择其他合适执行者。

## 5. 界面与统一激活

新增/编辑弹窗保留名称、执行工具、模型、职责和启用状态；删除操作范围选择器以及面向普通用户的 profile ID。必要时在能力说明中提供只读说明：

> 可使用已配置工具访问公共资料、处理任务文件；敏感操作由系统统一授权。

能力说明要结合实际工具证据，不能把默认权限描述成所有工具、模型均支持。用户不需要配置新的多选权限清单。

弹窗“保存”、启停确认和删除确认均只编辑当前设置草稿。界面打开、职责编辑、模型切换和 AI 改写不产生配置 revision，不探测/激活权限。仅设置页“保存并激活”提交完整候选，并在同一事务中验证、编译、探测及更新运行视图；严格空闲准入、冲突检测与补偿保持不变。

专门受限的自定义智能体不因选择器消失而自动扩大权限。它们保留原限制，必要时显示只读的系统限制说明；普通设置界面不提供绕过管理员限制的入口。

## 6. 已有配置迁移

1. 发布包含新 profile 语法、规则、投影和验证器的 Server；初始化的新安装直接使用系统基础方案。现有配置在仅升级软件或打开设置时不自动改写权限。
2. 编辑单个智能体草稿时准备该智能体的迁移，统一激活准备阶段再处理完整候选。服务端按真实 profile 定义识别普通 Pi/Codex 执行智能体，准备旧标准方案到 `standard-agent` 的有界迁移。不能根据 ref 名称或显示名称猜测；存在自定义约束的定义不参与自动迁移。
3. 用户点击唯一的“保存并激活”后，迁移与模型、连接、职责等其他修改一并提交。保留名称、启用状态、模型策略、用户职责、显式限制和既有资源参数；不因迁移启用原来停用的智能体。
4. 热更新白名单仅接受已安装的标准 profile 精确定义及符合条件的引用转换。任意 profile 参数、工具命令、后端边界变更仍走原有重启或拒绝规则，不能把整个 `permissionProfiles.*` 放入热更新白名单。
5. 任一验证、探测、运行视图更新失败时，沿用现有补偿机制，恢复配置与关联状态；草稿保留供修改。新任务采用新 revision，历史任务、固定 generation/attempt 与恢复继续使用原 revision 的权限含义。
6. 不修改旧不可变 revision，不清空授权审计，也不添加离线配置写入或独立“权限生效”入口。旧标准 profile 留作历史解析；新建普通智能体不再写入它们。

## 7. 模块所有权与实施范围

| Owner | 实施内容 |
| --- | --- |
| `src/resource/` | 新增纯基础 profile 与规则；保持目标归一化、资源边界、grant/budget 不变量 |
| `src/configuration/` | schema、系统默认配置、草稿准备、标准迁移和精确热更新分类；从用户可编辑字段中移除 profile 选择 |
| `src/routing/` 与现有 Planning 投影 | 分离工具证据、职责与授权事实；清理旧模板派生的研究/工程分工，不引入新分类路由 |
| `src/kernel/` | 继续唯一 grant/deny/escalate authority；读取代码维护的规则和已有授权事实，不解析职责来扩权 |
| `src/execution/`、`src/executor/` | 将基础 profile 传递到实际后端及恢复路径，提供可验证的工具和网络事实，不自定权限策略 |
| `src/management/`、`web/` | 返回可展示的能力/限制，移除选择器；只编辑草稿及调用既有统一激活接口 |
| `src/installation/` | 新安装默认使用基础方案；旧安装软件升级保持旧活动配置，后续迁移走正式配置事务 |

依赖方向遵循 ADR-0020：客户端只投影/提交，Configuration 负责配置生命周期，Kernel 决策，Runtime 应用，Storage 持久化事实。禁止新增 UI→Storage、Planner→权限写入、Runtime→职责解释的跨层路径。

本次没有数据库布局迁移计划。若实施确认需要持久化结构变化，必须补相应 Repository/migration 与 Docker 验收，不允许只改 UI 或 native 路径。

## 8. 验收与实施顺序

- [x] Resource/schema：基础 profile 同时支持普通文件操作和公共 HTTP(S)；私网、凭据、控制面及越权目标不能由该 profile 自动授权。
- [x] Configuration：新建普通智能体不需要 profile 输入；旧标准方案及别名精确迁移；自定义限制保留；职责修改不改变权限。
- [x] Routing/Runtime：同一智能体能查公共资料、写脚本分析并产出文件，也能查询开发文档、修改任务代码和运行测试；以模型/工具真实能力为前提，不依赖研究/工程标签。
- [x] 激活/恢复：所有编辑仅改草稿，唯一入口热激活；失败补偿完整；历史 revision 与恢复仍使用旧权限；回滚不重新解释旧 profile。
- [x] Web/Electron：不再出现二选一下拉框，无新的独立激活；多项草稿共同保存；敏感操作的具体授权沿用现有界面。
- [ ] Native 与 Docker：分别运行网络/文件/命令/受限目标用例，保存证据。包括“无工具/无网络”时的真实失败与提示，不能把权限默认开放等同于环境就绪。

按“资源/schema → 配置/默认值/迁移 → 路由与 Runtime 投影 → Web → 联合验收”实施。所有项完成后记录交付行为、验收命令、完成日期与 closing commit 状态，再标记实现完成。

## 9. 2026-10-06 本地交付与证据

交付范围：

- Resource 增加 `standard-agent`，保留历史 profile 的权限与规则身份；目标归一化、私网/凭据目标拒绝和敏感操作授权沿用现有路径。
- Configuration 新增纯迁移函数，精确识别默认定义与别名；保留原启用状态、模型、用户职责、资源参数及自定义限制。只清理完整匹配旧系统模板的分类与分工提示。标识冲突拒绝覆盖。
- 普通 Executor 创建/编辑接口不再接受权限输入。界面显示基础能力或自定义限制的只读说明；新增 profile 定义随智能体一起保存在页面草稿。
- 唯一激活事务准备完整迁移；精确前向/反向变化可热更新，任意参数变化不进入白名单。回滚不再次归一化；历史 revision 不改写。新安装直接生成基础方案，单纯升级不迁移现有权限。
- 路由由已有能力编译器结合 CLI 操作与模型证据推导交付能力，不根据职责授予权限，也不虚构图像能力。Docker 出口选择读取已授权 revision 中的 profile 定义，支持别名。
