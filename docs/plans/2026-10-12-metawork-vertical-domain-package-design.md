# MetaWork 垂类化架构方案

## 共享底座、Domain Package 与应用组合设计（Review 草案）

- **日期：** 2026-10-12
- **状态：** 讨论稿，待 Review，尚未实施；本文中的接口、目录与接入能力均为建议，不代表现有实现。
- **目标：** 基于当前 MetaWork，接入第一个垂直行业，跑通一个真实业务闭环。
- **范围：** 不建设通用行业平台，不引入第二套 Agent 执行与调度体系。
- **试点行业：** 待定。视频生产仅用于说明架构，不代表已选择该行业。

---

# 一、总体结论

本方案建议采用：

> 从当前 MetaWork 中明确共享底座，在现有执行主链上接入 Domain Package，通过应用组合形成垂类 MetaWork。

产品关系为：

```text
普通 MetaWork
= MetaWork 共享底座
  + 普通应用组合

垂类 MetaWork
= MetaWork 共享底座
  + 行业 Domain Package
  + 行业应用组合
```

其中：

```text
MetaWork 共享底座
├── Core：核心任务运行与控制能力
├── 通用适配与基础设施
└── 可复用产品组件
```

**当前完整的 MetaWork 产品不全部等于 Core，但其中大部分通用能力可以被垂类版复用。**

行业执行主链保持不变：

```text
Planner 提案
    ↓
ControlKernel 授权
    ↓
Execution Runtime 启动执行
    ↓
Executor 使用通用工具和行业工具完成工作
    ↓
现有验收、发布与交付链路
```

不新增一个替代 Executor 的 Domain Action Coordinator，也不新增独立行业调度器。

# 二、本阶段目标与边界

## 2.1 本阶段目标

1. 明确当前 MetaWork 的共享能力、产品组合和行业扩展边界。
2. 用一个 Domain Package 承载行业知识、模型、规则和工具。
3. 让现有 Planner 理解行业任务，让 Executor 完成行业工作。
4. 对业务系统操作实施必要的权限、审批、校验和防重复控制。
5. 保留普通 MetaWork 的现有能力，不因行业接入产生产品分叉。
6. 用真实业务流程验证架构是否可用、可维护。

## 2.2 本阶段不做

- 行业插件市场、动态安装和热卸载。
- 第三方行业开发者平台。
- 多行业同时运行或运行中切换行业。
- 通用 Ontology 引擎、图数据库平台。
- 通用流程 DSL、可视化流程设计器。
- 新的 Agent Runtime、任务调度器或通用审批引擎。
- 企业级多租户和复杂组织权限平台。
- 全仓库重构或提前拆分多个独立仓库。

本阶段的“快速落地垂类”是指：

> 复用共享底座，只补充行业差异，快速组合出可交付产品。

不是只换提示词，也不是自动生成一套完整行业系统。

# 三、当前 MetaWork 与共享底座的关系

## 3.1 当前 MetaWork 是完整产品

从逻辑上看，当前产品包含：

```text
当前 MetaWork
├── 核心运行能力
│   任务、规划、授权、执行、恢复、验收
│
├── 通用适配与基础设施
│   模型、Executor、存储、渠道等具体接入
│
├── 可复用产品组件
│   Web、Desktop、TUI、设置、轨迹、安装升级
│
└── 普通应用组合
    默认配置、功能入口、启用组件、产品装配
```

这些内容大部分可以复用，但不应该都归入一个庞大的 `Core` 模块。

## 3.2 Core 的定义

本方案将 MetaWork Core 定义为：

> 负责通用任务运行与控制的核心能力及其契约。

主要包括：

- Task、Subtask、Attempt 等运行模型和生命周期。
- Work Graph 的依赖、交接和执行规则。
- Planner 提案契约与校验。
- ControlKernel 的授权、调度、取消和恢复决策。
- Execution Runtime 的执行生命周期管理。
- 上下文引用、结果验收和产物授权等通用契约。

Core 不理解具体行业中的：

```text
视频方案、证券、供应商、设备、采购订单……
```

这些属于 Domain Package。

## 3.3 其他共享能力

| 类别 | 示例 | 定位 |
|---|---|---|
| 通用适配与基础设施 | Pi / Codex 接入、模型接口、数据库适配、外部渠道 | 支撑 Core 运行，可以共享 |
| 可复用产品组件 | Web 对话、执行轨迹、设置、文件预览、Desktop 壳、TUI | 提供产品体验，可以共享 |
| 产品支撑能力 | 安装升级、官方账号、授权服务、计量计费接入 | 按产品部署方式复用 |
| 普通应用组合 | 默认智能体配置、功能入口、启用组件 | 定义普通 MetaWork 的产品形态 |
| 行业应用组合 | 行业包装配、连接器配置、行业页面与默认设置 | 定义垂类产品形态 |

这是**逻辑职责划分，不是立即搬迁代码的计划**。现有模块可能同时包含契约和具体实现，应在实际接入时逐步明确。

## 3.4 普通版与垂类版的关系

```text
                 MetaWork 共享底座
        ┌─────────────────────────────┐
        │ Core                        │
        │ 通用适配与基础设施          │
        │ 可复用产品组件              │
        └─────────────────────────────┘
                   │         │
          ┌────────┘         └────────┐
          ↓                           ↓
    普通 MetaWork                垂类 MetaWork
    普通应用组合                 行业 Domain Package
                                 行业应用组合
```

垂类版继续复用当前的聊天、轨迹、模型设置、文件预览和安装升级能力，只增加必要的行业差异。

**普通版不需要为了形式对称，被强行改造成一个“通用行业包”。**

# 四、总体运行架构

```text
                      用户
                       │
          通用界面 / 必要的行业页面
                       │
                 现有 Gateway
                       │
                    Planner
           行业术语、流程指导、只读摘要
                       │
                  Work Graph
                       │
                 ControlKernel
                       │
               Execution Runtime
                       │
                    Executor
                       │
          ┌────────────┴────────────┐
          │                         │
        通用工具                  行业工具
     文件、检索、计算等       Domain Query / Action
                                    │
                           业务规则与访问校验
                                    │
                                Connector
                                    │
                         行业数据 / 外部业务系统
```

Domain Package 提供两类内容：

### 提供给模型的指导

- 行业术语。
- 分析方法。
- 流程说明。
- 工具说明。
- 检查清单。
- 输出规范。

### 由代码强制执行的能力

- 业务对象与状态。
- 数据访问控制。
- 参数和前置条件校验。
- 审批校验。
- 防重复提交。
- 外部调用和业务记录。

**指导材料可以告诉 Executor 应该怎么做，但不能代替服务端的强制校验。**

# 五、各部分职责

| 部分 | 职责 | 不负责 |
|---|---|---|
| Planner | 理解需求、查询必要概要、提出计划 | 直接操作业务系统 |
| ControlKernel | 通用授权、调度、恢复等控制决策 | 执行行业业务逻辑、查询外部系统 |
| Execution Runtime | 管理 Attempt、执行资源与执行衔接 | 决定行业业务规则 |
| Executor | 推理、分析、生成内容、调用工具完成工作 | 绕过工具边界操作受控业务系统 |
| Domain Package | 行业模型、知识、规则、工具与连接器 | 调度 Executor、直接改变 Core 生命周期 |
| 应用组合 | 装配共享底座、行业包、配置和界面 | 承担业务推理或任务调度 |

核心原则：

> Core 负责如何可靠地执行；Domain Package 定义行业工作需要的知识、规则和操作；Executor 使用这些能力完成工作。

# 六、Domain Package 设计

行业包按试点需要实现以下内容，不要求第一版全部具备。

| 部分 | 内容 |
|---|---|
| Domain Model | 业务对象、关系、状态、版本 |
| Guidance | 行业术语、方法、检查清单、输出规范 |
| Workflow Guidance | 常见流程、必要步骤和完成标准 |
| Query Tools | 查询对象、业务状态、资料和证据 |
| Action Tools | 保存、提交、发布等业务操作 |
| Business Rules | 前置条件、审批要求、业务约束 |
| Connectors | 行业数据和外部系统适配 |
| Storage | 必要的行业事实、对象引用和操作记录 |
| UI | 必要的业务对象、审批内容和结果展示 |

## 6.1 业务对象

仅围绕试点闭环建模。

例如视频生产可能需要：

```text
Project
Brief
Asset
VideoPlan
```

重要对象至少明确：

- 身份与来源。
- 当前状态。
- 必要的内容版本。
- 访问范围。
- 可执行操作。

如果对象已有外部权威系统，优先保存引用和必要摘要，不另建一个相互竞争的业务事实源。

## 6.2 流程指导

描述：

- 输入和目标。
- 通常经过哪些步骤。
- 哪些步骤可以调整。
- 哪些条件必须满足。
- 最终如何验收。

它辅助 Planner 和 Executor，不成为独立流程引擎。

例如“发布前必须审批”不仅出现在流程说明中，还必须在发布工具中强制检查。

## 6.3 行业工具

```text
Query：获取业务信息
Action：改变业务状态或触发外部操作
```

例如：

```text
get_project
list_project_assets
get_video_plan

save_video_plan
submit_video_generation
get_video_generation_status
```

Domain Action 是 Executor 使用的业务工具，不是替代 Executor 的执行主体。

# 七、与现有 MetaWork 的接入方式

## 7.1 Planner 接入行业规划信息

Planner 获得：

- 行业术语。
- 可用能力与工具概要。
- 常见流程。
- 交付标准。
- 必要的业务对象摘要。

分工为：

```text
Planner：获取规划所需的概要
Executor：获取执行所需的详细资料
```

现有 Planner 入口受到严格控制，不能假设放入一个 Skill 或 MCP 配置就能自动接入。应核查现有上下文契约，必要时做最小扩展。

## 7.2 Work Graph 优先复用

第一版通过现有机制表达：

- 工作目标。
- 验收标准。
- 依赖与交接。
- 执行能力要求。
- 受控输入和结果引用。

不提前增加 `execute_action` 节点，也不要求 Planner 为每一次工具调用规划一个 Subtask。

只有实际场景证明现有结构无法安全表达业务对象引用或工具范围时，才补充最小通用契约。

## 7.3 Executor 接入受控工具

```text
Executor
   ↓
受控工具入口
   ↓
Domain Query / Action
   ↓
Connector
   ↓
业务系统
```

Runtime 为调用提供可信身份和范围：

- 所属账号或工作区。
- 当前 Task / Attempt。
- 可用工具范围。
- 行业配置版本。

不能相信模型自报的账号、权限或“已经审批”。

具体传输方式根据现有 Harness 能力决定，不预先规定必须新增 MCP 服务或插件框架。

## 7.4 Kernel 保持原有控制边界

Kernel 不在决策过程中：

- 查询行业数据库。
- 调用外部服务。
- 执行有副作用的行业代码。

行业工具返回待审批、失败、已提交、结果不确定等事实；需要改变任务生命周期时，进入现有控制链。

不允许行业代码自行重排 Work Graph、切换 Executor 或直接写 Task 状态。

# 八、业务操作的安全与可靠性

## 8.1 任务授权不等于动作批准

```text
允许编写方案
≠
允许花费预算执行
≠
允许对外发布
```

行业动作实际调用时，需要检查：

1. 调用身份和 Attempt 是否有效。
2. 是否允许使用该工具。
3. 目标对象是否可访问。
4. 参数和对象状态是否合法。
5. 必要审批是否存在且有效。
6. 是否已经执行过同一次业务操作。

这些职责由接入边界和行业工具实现承担，不新增独立 Coordinator。

## 8.2 审批绑定具体内容

审批应对应：

```text
目标对象
动作类型
关键参数
内容版本
批准人
```

内容改变后，不能默认沿用原批准。

现有运行权限审批不等于业务内容审批。可以复用已有机制，但是否满足试点需求，需要验证。

## 8.3 外部操作防重复

例如外部平台已接收请求，但网络断开：

```text
不能确认结果
≠
确定执行失败
```

需要依据外部 API 能力：

- 使用幂等键。
- 保存请求关联和外部编号。
- 超时后先查询确认。
- 无法确认时进入明确的待核实状态，而不是盲目重发。

幂等身份应对应业务操作，不能因为创建了新 Attempt 就自动重复提交。

## 8.4 取消与凭据边界

- 停止 MetaWork，不一定意味着外部操作已取消。
- 外部系统不支持撤销时，必须明确告知。
- 业务生产密钥保留在受控服务端，不直接交给 Executor。
- 上线前检查文件、环境变量和网络是否存在绕过工具的路径。

如果执行环境无法形成可信边界，先限制为只读或低风险操作，不能只靠提示词宣称安全。

# 九、外部异步任务的处理

第一版采用简单方式：

```text
Executor 提交操作
    ↓
保存外部任务编号
    ↓
间隔查询
    ↓
获取结果
    ↓
检查并交付
```

其中：

| 记录 | 含义 |
|---|---|
| MetaWork Attempt | Executor 的一次执行 |
| 外部任务编号 | 外部平台的一次处理 |

不强制建设通用 `GenerationJob` 模块，保存必要的关联、编号和确认记录即可。

必须区分：

```text
提交成功
≠
外部处理完成
≠
结果验收并交付
```

如果试点出现等待数小时、需要释放 Executor 或依靠回调继续执行的真实需求，再研究与现有恢复链路的衔接。

# 十、仓库管理

## 10.1 管理原则

> 单仓库、主干开发、逻辑隔离、静态组合。

- 不复制 Core。
- 不复制整个 MetaWork 产品。
- 不建立长期垂类分支。
- 不提前拆成多个独立仓库。
- 不要求先把共享底座完整物理拆包，再接入行业。

## 10.2 建议结构

保留现有布局，新增必要目录：

```text
metawork/
├── src/
│   ├── planning/
│   ├── kernel/
│   ├── execution/
│   ├── executor/
│   ├── storage/
│   └── domain-integration/     # 最小接入契约与适配
│
├── domains/
│   └── <pilot>/
│       ├── model/
│       ├── guidance/
│       ├── workflows/
│       ├── tools/
│       ├── rules/
│       ├── connectors/
│       ├── storage/
│       └── tests/
│
├── apps/
│   ├── desktop/                # 已有应用
│   └── <pilot>/
│       └── composition.ts      # 行业组合入口
│
├── web/src/
│   └── domains/<pilot>/        # 必要的行业页面
│
└── docs/
    ├── plans/
    ├── adr/
    └── domains/<pilot>/
```

注意：

- `src/` 不等于全部都是 Core，它仍可能包含共享适配和产品支撑代码。
- `domain-integration` 是暂定逻辑位置，不是计划建设一个庞大 Domain Runtime。
- 行业前端只保留一个实现位置，不复制两套工作台。

## 10.3 依赖与组合

```text
普通组合入口
  → 共享底座
  → 普通配置

行业组合入口
  → 共享底座
  → 行业包
  → 行业配置
```

具体行业只在组合入口被选择。

行业包通过公共契约接入，不直接导入 Kernel 内部实现或修改 Core 表。

通过代码审查责任和依赖检查约束边界。

# 十一、数据、版本与发布

## 11.1 数据所有权

| 数据 | 所有者 |
|---|---|
| Task、Subtask、Attempt、控制决策 | Core |
| 行业对象、内容版本、业务规则记录 | Domain Package |
| 外部订单或生成任务的真实状态 | 外部业务系统 |
| 外部操作关联与确认记录 | 行业工具实现 |
| 通用产物与交付 | 现有 Artifact / Delivery 模块 |

行业数据可以沿用当前存储基础，使用独立表和 Repository，不必立即拆数据库。

但本地数据库与外部 API 没有天然的原子事务，仍需要幂等和状态确认机制。

## 11.2 版本策略

第一版采用：

> 同仓、联合测试、联合发布，记录明确的组件版本身份。

发布信息包含：

- 产品版本。
- 源码版本。
- 行业包身份与版本。
- 配置版本。
- 数据 Schema 版本。

运行任务应关联必要的行业配置或规则版本。

不过，记录版本不代表已经支持旧代码运行或完整历史重放。遇到不兼容升级时，应通过现有升级门禁阻止或要求先处理未完成工作，不承诺跨版本无缝恢复。

## 11.3 产品发布

- 保留普通版构建。
- 增加一个明确的试点行业组合。
- 暂不提供任意行业运行时切换。
- 普通版与试点版初期使用独立测试数据根。
- 安装、备份、迁移和回退继续遵循现有管理机制。

# 十二、实施路径

## 阶段一：确定试点业务闭环

选择一个有真实负责人、数据可得、结果可验收、风险可控的流程。

产出：

- 端到端流程图。
- 核心对象清单。
- 查询与动作清单。
- 审批点。
- 输入输出样例。
- 验收标准。
- 本阶段不做的内容。

## 阶段二：完成架构与代码盘点

把现有能力分为：

```text
Core
共享适配与基础设施
可复用产品组件
普通应用组合
```

同时核查：

- Planner 上下文接入。
- Executor 工具装配。
- 可信调用身份。
- 凭据边界。
- 权限与业务审批差异。
- 数据迁移与版本约束。

产出：**现状、缺口和最小改动清单**。

不在这一阶段全面重构仓库。

## 阶段三：跑通最小链路

实现：

```text
一个行业查询
+ 一个行业动作
+ 一个 Fake Connector
+ 一个完整任务
```

验证从用户请求到结果交付的整条主链。

以业务跑通为里程碑，不以“通用接口全部设计完成”为里程碑。

## 阶段四：接入真实系统

顺序：

```text
只读查询
→ 低风险写入
→ 需要审批的操作
```

补齐参数校验、审批绑定、幂等、超时确认和取消语义。

## 阶段五：完善体验并试运行

优先复用现有界面，只补充必要的：

- 对象详情。
- 内容版本或方案对比。
- 审批内容。
- 行业结果展示。

由真实业务人员使用，记录失败原因、人工修改和结果质量。

# 十三、验证计划

## 13.1 架构验证

- Core 不包含具体行业判断。
- 行业包不直接修改 Task / Attempt 状态。
- 不存在第二套 Agent 调度体系。
- Executor 仍是行业任务执行主体。
- 普通版不依赖行业服务也能正常运行。
- 共享界面和基础设施没有被重复复制。

## 13.2 业务验证

- 正确引用业务对象。
- 使用行业方法和输出规范。
- 工具操作满足业务规则。
- 验收依据真实结果和证据，而不是模型自述。
- 业务人员能够检查并接受交付物。

## 13.3 安全与可靠性验证

| 场景 | 预期结果 |
|---|---|
| 未审批调用高影响动作 | 拒绝 |
| 审批后内容发生变化 | 不沿用失效审批 |
| 访问未授权对象 | 拒绝 |
| 重复提交同一业务操作 | 不产生重复副作用 |
| 外部已接收但响应丢失 | 先确认，不盲目重发 |
| Executor 中断后恢复 | 能关联已有外部操作 |
| MetaWork 取消但外部仍在运行 | 准确展示状态 |
| 工具仅返回“已提交” | 不误报最终完成 |
| 行业包配置缺失 | 明确不可用，不破坏普通版基础能力 |

高风险授权与关键防重复测试作为上线硬门槛。

业务成功率、耗时和成本目标，根据试点人工基线制定，不提前给出没有依据的指标。

## 13.4 测试层次

1. 现有 Core 与普通版回归测试。
2. 行业对象、规则和连接器单元测试。
3. 工具接入契约测试。
4. 完整业务端到端测试。
5. 中断、超时、重复请求等故障测试。
6. 真实业务验收。

# 十五、Review 核心决策

本方案建议确认以下六点：

1. **当前 MetaWork 不全部等于 Core。**  
   应区分核心运行能力、共享适配、产品组件与应用组合。

2. **普通版与垂类版共享底座。**  
   二者是不同产品组合，不是复制出来的两个分叉。

3. **现有执行主链保持不变。**  
   行业任务仍由 Executor 完成。

4. **Domain Package 提供行业能力，不接管调度。**  
   主要承载模型、知识、规则、查询工具、动作工具和连接器。

5. **先做最小接入，不做全面重构。**  
   不先拆 Core 包，不新增独立 Coordinator，不提前建设平台。

6. **先用一个业务闭环验证。**  
   后续行业增多，再决定哪些重复需求值得抽象。

**最终定位：MetaWork 提供可复用的任务执行与产品底座，Domain Package 提供行业差异，应用组合将二者装配成具体产品。第一阶段的成功标准，是在不复制产品、不破坏原有执行体系的前提下，交付一个真正可用的垂类 MetaWork。**
