# 任务状态简化设计

- 日期：2026-10-22
- 状态：待用户评审，未实施；本轮仅修改设计文档。
- 本文是本次任务状态改造的唯一产品目标方案，仍待评审；[技术落地方案](2026-10-22-task-state-implementation-plan.md)细化代码入口、事务、恢复、迁移和验收，不另建任务规则。两份文档均未实施，现行 ADR 在方案批准实施前保持不变。

## 一句话

任务就是依次完成用户要求的工作：能继续就执行，需要用户就停下来，做完就成功，确定做不成就失败。

## 六个状态

| 状态 | 唯一含义 | 如何离开 |
| --- | --- | --- |
| 排队 | 已准备继续，等待执行名额 | 获得名额后执行，或用户取消 |
| 执行中 | 系统正在做事，或正在进行有明确期限的自动重试 | 成功、失败、待处理或取消 |
| 待处理 | 必须由用户补充信息、确认结果或核实异常，系统不会自动继续 | 用户处理后重新排队，或取消 |
| 成功 | 用户要求的必需工作全部完成 | 本次任务结束 |
| 失败 | 必需工作确定失败，且本轮不再自动尝试 | 本次任务结束 |
| 取消 | 用户终止了任务 | 本次任务结束 |

不再同时维护 raw status、canonical lifecycle、userState 三套近似状态。数据库、列表、详情和总览使用同一任务状态。发布、启动服务、重试、停止清理只是执行阶段；缺材料、等待接受、结果未知只是待处理原因，都不增加状态。

## 一套转换规则

```text
新任务 → 排队 → 执行中 → 成功 / 失败 / 取消
                    ↓
                  待处理 → 排队 → 执行中
```

排队和待处理也可以取消。每次转换记录原因；同一操作重复到达不重复执行。成功、失败、取消后不自动复活；后续明确重试创建关联的后续任务，只处理未完成部分，保留原任务结论。

1. **有实际动作，才能叫执行中。** 生成代码、发布文件、启动服务、有限次数重试、停止进程都算动作；没有动作，也没有明确的下一次重试时间，就不能一直运行。
2. **等待用户，必须说清要用户做什么。** 接受结果、补材料、确认未知外部结果属于待处理。已确定的端口冲突、命令不存在、重试耗尽属于失败，不统一塞进待处理。
3. **成功按用户要求判断。** 只要求交付代码，交付即成功；要求交付并启动服务，两项都成功才算成功。服务启动也要进入这条工作链，不能放在任务收尾外面另行处理。
4. **失败保留已完成部分。** 代码交付成功、服务启动失败，整体就是失败，并显示这两项事实；不撤销代码，也不重跑已经完成的工作。
5. **重试有边界。** 仅对已授权且可安全重复的临时故障自动重试，有次数和时间上限。确定失败直接收尾；外部操作结果未知先核实，不假定失败后重复执行。

## 一条队列规则

同一会话一次执行一个任务；旧任务停止执行并完成必要清理后，下一个任务开始。

- 排队任务不占执行名额。
- 待处理任务在安全停下后让出名额；用户处理后重新排队。
- 成功、失败、取消都要收尾并让出名额。
- 进程尚未退出、文件还在写或外部动作结果未知时，暂不放行后继，明确显示“正在清理”或“需核实，暂不能启动后续任务”。不能为了清空队列假装清理成功。

任务状态与资源锁分工明确：状态说明用户工作处于什么结果，资源锁防止旧操作与新操作冲突。锁不是另一套任务生命周期，也不能因为任务未成功就一直持有。已交付的常驻服务由服务管理器接管，不长期占用任务执行名额。

## 多个子任务也按同一原则

独立分支可以继续，依赖失败分支的工作不能继续。全部分支收束时，按以下顺序决定任务结果：

1. 用户已取消：停止并收尾为取消。
2. 还有可以自动推进的工作：执行中。
3. 必需工作已确定失败，且本轮没有恢复动作：失败，保留其他成果。
4. 必须等用户处理才能继续：待处理。
5. 必需工作全部完成：成功。

子任务自身等待其他子任务，不等于整个任务待处理。并行运行中可以同时展示局部失败或待确认事项。若所有分支都停下却不符合上述任何条件，这是系统异常，必须给出明确原因，不能默认运行。

## 当前案例的正确行为

```text
待处理：完成证明不足，等待接受
→ 用户接受
→ 排队并获得名额
→ 执行中：发布代码、启动服务
→ 失败：8788 端口被占用，代码已交付
→ 确认没有残留操作，释放名额
→ 8789 后续任务开始执行
```

“未认证”保留为原执行记录的历史事实；当前显示“用户已接受”。不能继续显示待接受，更不能用它覆盖后来的服务启动失败。

## 首要要求：所有模块使用同一个任务结论

一致性不是各模块碰巧显示相同文字，而是它们不能各自决定任务状态。以下是实施硬约束：

1. **一个来源、一个修改入口。** Task Domain 持久化的当前任务状态是唯一权威来源。Kernel 按统一规则决策，Runtime 通过唯一入口应用；调度、恢复、命令和客户端不维护另一份任务结论，也不直接绕过入口改状态。服务、进程和子任务可以保留自身运行状态，但只能上报事实，由统一规则决定对 Task 的影响。
2. **一次变更，完整落地。** 同一数据库内属于一次转换的任务状态、原因、版本、操作应用记录与必要后续事件在同一事务提交；名额释放和后继预约遵循自己的原子事务与任务版本校验。需要跨事务推进的步骤由持久化事件衔接，不能依赖内存回调或客户端在线。
3. **异步动作明确显示进度。** 数据库事务无法同时保证进程已经退出或页面立即刷新。尚未完成的清理必须真实显示，队列不得提前放行；客户端消费带版本的已提交状态，拒绝旧消息覆盖新状态，断线后从当前快照补齐。允许传输延迟，不允许长期分歧。
4. **恢复沿用同一规则。** 正常执行、重复请求、重启恢复共用转换规则和动作完成判断。恢复只补完中断步骤；已完成步骤不重复执行，旧事件不能让任务倒退或复活。
5. **按完整链路验收。** 每次状态变化都同时核对任务、子任务/操作、名额、队列、列表和详情；不能以某个模块的单元测试通过代替整体通过。

实施前列清所有读写任务状态的入口；每条链路同时更新生产者、存储、恢复、调度和展示消费者，并删除旧判断。不能只更新几个模块就宣布完成。涉及持久化契约变化时配套迁移与安装升级验证，新旧状态写入逻辑不得同时运行。

当前案例的联动验收必须证明：服务启动失败事实已保存 → Task 显示失败及明确原因 → 已交付代码仍可见 → 清理结束后释放名额 → 后继任务只启动一次 → 各页面读取同一版本的任务结论。再分别在这些步骤之间模拟崩溃、重复事件和断线重连，验证仍能得到相同结果。

## 实施只做三件事

1. **统一状态入口。** 一份状态定义、一张转换表、一个修改入口；失败、等待用户和终态重放都走它。客户端直接读取，不再自行猜测。
2. **统一操作收尾。** 执行、发布、交付、服务启动都报告成功、确定失败或需用户处理；使用同一任务判断规则。正常运行和重启恢复使用相同的完成判断。队列只在安全收尾后推进。
3. **删除重复判断并验收。** 替换旧的状态映射、总览统计和分散收尾分支；迁移旧任务时根据证据分类，无法确认的进入待处理，不批量猜测成功或失败。

这不是减少必要的进程、租约与审计记录，而是让这些内部记录不再各自发明任务状态或恢复政策。仍沿用 Task Domain 管状态、Kernel 作决策、Runtime 执行、现有调度器管理队列的职责。

## 验收只看六个结果

- 明确失败能结束，不一直转圈。
- 等用户的任务安全停下后不挡后续任务。
- 已成功的工作不因恢复而重复执行。
- 取消与失败都不遗留偷偷运行的进程；无法确认时明确提示并保留隔离。
- 重启、重复点击不改变结论或重复副作用。
- 列表、详情、总览及不同客户端显示相同状态与原因。

联动测试必须覆盖端口冲突、接受后交付失败、局部子任务阻塞、多个待处理原因、取消与完成竞争，以及状态落库后或名额释放后的崩溃恢复。每个场景同时验证任务状态、队列推进与页面展示的一致性。
