# MetaWork 商业化前的任务执行简化方案

- 计划日期：2026-10-15。
- 状态：实施中（2026-10-15 用户授权）；严格按五阶段推进，各阶段完成后记录端到端证据与目标 review。
- 技术落地细节见：[任务执行可靠性技术方案](2026-10-15-task-execution-reliability-technical-design.md)。
- 目标：解决近期反复出现的任务阻塞、状态混乱、错误完成和恢复重复执行问题，形成可以面向付费用户交付的简单执行流程。
- 范围：Planner 拆解、Executor 执行、结果拼装、任务状态和恢复入口。
- 昨天已经通过的真实调研任务不再重跑，不作为本方案关闭条件。

## 1. 先说结论

当前版本的问题不是某一个小 Bug，而是把一次任务拆成太多互相影响的状态和补救路径。`Task`、`Subtask`、`Attempt`、`Dispatch`、`Retry Wake`、`Publication`、`Lease`、`Kernel application` 和多个页面各自保存一部分状态；这些状态一旦不同步，用户就会看到“已经做了但显示阻塞”“已经退出但仍在运行”“文件有了但任务没完成”等情况。

继续在这套复杂状态上增加判断，只会继续增加出错机会。本方案采用一个更简单的产品模型：

```text
Planner 拆成几个可执行的小任务
  → 每个小任务交给 Executor 完成
  → MetaWork 保存 Executor 结果
  → 按依赖把结果交给下一个小任务
  → 汇总成用户能看懂的最终状态
```

MetaWork 的核心价值是**安排和拼装**，不是重新当一个 Executor 去评判 Executor 的业务质量。

## 2. 三条不可妥协的原则

### 2.1 MetaWork 调用 Executor，能力必须和用户直接调用一致

同一个 Executor、同一个模型、同一套工具和同一工作条件下，用户直接调用和 MetaWork 调用必须具备相同的执行能力。允许文字结果因模型随机性和外部网站变化而不同，但不允许出现：直接调用能写文件，MetaWork 调用只能写建议。

这里的“一致”指运行条件和调用链一致，不指每个生产任务都执行两遍，也不指两次文字结果逐字相同。当前代码已有配置 revision、Provider/Model、AgentClass、权限和隔离工作区，但必须把它们视为一次完整的运行绑定。MetaWork 不能偷偷改变：

- Provider 协议和 Base URL；
- 模型和工具集合；
- 工作目录、输入文件和历史结果；
- 权限、网络和凭据；
- Planner 交给 Executor 的真实目标。

如果绑定不一致，任务应在开始前报出具体原因并停止。不能用更复杂的“完成审查”掩盖 Executor 接入错误。

### 2.1.1 怎么验证，不重复执行用户任务

验证分成两层：

**每次生产任务只做启动前核对。** `agent-runtime-renderer.ts`、`runtime-private-binding-resolver.ts` 和 `pi-cli-driver.ts` 共同生成本次 Executor 的运行清单，并保存一个绑定指纹。清单至少包含：

- 实际 Executor 程序及版本；
- Provider 协议、Base URL、模型和配置 revision；
- 启用的工具及权限 profile；
- 工作目录、输入引用和网络/凭据边界；
- Planner 交给 Executor 的目标与输出要求。

`SubtaskAttemptRunner` 启动前检查这份清单完整且与 Kernel 授权绑定一致。缺字段、绑定被替换或运行适配器不匹配，就不启动任务并说明差异。生产中只启动一个 Executor，不旁边再跑一份“直接调用”作比较。

**只有发布前或适配器变更时做隔离对照测试。** 使用一个无副作用的小任务，分别走用户直接使用的 Executor 入口和 MetaWork 的正式启动入口，核对工具是否可用、文件是否能读写、命令是否能执行、结果是否能返回。这个测试是验证适配器的契约，不是用户任务的影子执行，也不把两次结果当作业务结果。

如果用户直接调用的是任意自定义配置，而 MetaWork 无法读取或复现它的协议、工具和权限，就不能声称两者一致。产品应使用同一份受管理的运行绑定，或在任务开始前明确提示“当前运行条件无法与直接调用保持一致”。

### 2.2 MetaWork 只做简单事实核对

Executor 返回成功或失败后，MetaWork 只核对：

1. 结果是否属于本次授权执行；
2. Executor 是否已经结束；
3. Planner 声明的交付物是否存在；
4. 结果是否可以传给依赖它的下游。

MetaWork 不重新评价报告质量、代码质量、调研深度，也不要求所有任务产出文档。没有声明文件的回答不需要文件；声明了代码修改就核对工作区修改；声明了外部动作就核对动作回执。

### 2.3 用户只看到少数状态

内部可以保留审计和资源事实，但产品界面只保留四个主状态：

| 用户状态 | 含义 |
| --- | --- |
| 等待中 | 尚未开始，正在等前置结果或执行名额 |
| 执行中 | 至少一个 Executor 正在工作，或正在完成必要交付 |
| 需要处理 | 没有安全的自动下一步，需要用户补材料、修配置或确认结果 |
| 已结束 | 已完成、已失败或已取消，原因作为说明展示 |

“阻塞”不再作为产品状态；内部旧字段可以暂时保留，但只能映射为“需要处理”。`canCancel`、租约、最后一条日志和数据库原始状态都不能单独决定页面显示什么。

## 3. 基于当前代码的架构取舍

### 3.1 保留的东西

- Planner → Kernel → Runtime → Executor 的主方向，符合 ADR-0020。
- 工作图中的依赖、handoff 和已有成果引用。
- Executor 的独立进程、工作区隔离和权限边界。
- Attempt 历史、取消清理、资源租约和必要的崩溃恢复事实。
- `AttemptTerminalService` 的终态事务，以及 `TaskView` 作为状态投影入口。

这些是执行安全和审计需要的事实，不应该因为界面复杂就删除。

### 3.2 必须改变的东西

- `TaskView` 对外不再暴露当前十多种阶段；内部阶段只在详情或日志中使用。
- `wait_for_capacity`、依赖等待和 Executor 故障不再随意写成整个 Task 的 `blocked`。
- `completion-protocol.ts` 不再因为缺少 trailer 就自动合成 certified 的完成结果；正文可以展示，但没有必要事实时不能推进下游。
- `WorkspacePublicationWorker` 不得先把子任务标成完成，再把用户文件发布失败吞成 warning。
- Web、Timeline、Dashboard、TUI、飞书删除各自从原始状态推断运行状态的代码，只读统一投影。
- 不再为每一种异常增加新的 Task 状态、按钮或恢复协议。

### 3.3 不迁就当前不合适的设计

如果现有状态字段、恢复分支或 Completion Protocol 无法清楚表达上述简单规则，就修改或合并它们。方案不以“当前已经有这个字段”为理由继续保留错误设计。

但不做无目的的大搬迁：只删除重复判断、合并重复状态、修正错误顺序；Attempt 历史和必要的资源安全事实继续保留。

## 4. 一个简单的任务模型

Planner 对每个小任务只需要给出：

- 目标：Executor 要完成什么；
- 依赖：需要哪些前置结果；
- 交付：回答、工作区修改、文件或外部动作结果中的一种或几种。

当前 Planner 的 `deliveryKind: 'edit' | 'report'`、`artifacts`、`handoffs` 和 `acceptance` 已能承载大部分需求，不先扩展成一套复杂的交付语言：

- `report` 可以是文字回答，也可以是用户明确要的报告、表格、图片或 PPT；
- `edit` 用于代码和配置修改，不默认生成报告；
- 安装、卸载、浏览器和外部系统操作以动作结果或回执为主，没有文件要求就不生成文档。

只有 Planner 声明的交付物才需要 MetaWork 核对。MetaWork 不从自然语言关键词猜测“应该有一份文档”。

## 5. 多个小任务如何运行

### 5.1 运行规则

- 有一个小任务正在执行，其他独立小任务可以同时执行；
- 小任务等待名额或前置结果，只标记它自己等待；
- 一个小任务失败，只影响它自己和依赖它的下游；
- 汇总小任务只有在所需结果真实可读时才启动；
- 所有必要交付完成后，整体才结束。

这直接解决“第三个子任务排队，整个任务被写成阻塞”和“一个 Executor 探测失败，兄弟任务也停住”的问题。

### 5.2 不再增加任务级补丁

等待、失败、恢复和清理都通过已有 Kernel 事件和事实处理。只保留一个用户动作：**继续未完成部分**。

后台根据事实选择：继续等待、补存结果、补交文件、重做失败的小任务或请求用户确认。已经完成的小任务不重跑；外部动作结果不确定时先核对，不能盲目重复。

## 6. 实施顺序

### 第一步：先消除 Executor 接入差异

检查当前 Pi、Codex 和 Provider 运行绑定在协议、工具、工作目录、权限、输入和输出通道上的差异。修复后用小型隔离任务证明读、写、命令和需要的网络能力可用。

这一步不过，后面所有“任务是否完成”的判断都没有意义。不能先加更多完成检查。

### 第二步：重做简单的状态汇总

在 `src/task/task-view.ts` 建立四种主状态的唯一映射，保留内部事实用于详情。同步修改 `src/management/execution-projector.ts`、Web 活动列表、Timeline、Dashboard、TUI 和飞书，删除原始状态和 `canCancel` 推断。

### 第三步：收敛等待作用域

检查 `ControlKernel` 产生 `wait_for_capacity`、`wait_for_retry`、`block_work` 的条件，以及 `KernelExecutionRuntime` 的应用路径。等待只属于对应的小任务；只有整个任务没有执行分支、没有自动推进者时，才进入“需要处理”。

### 第四步：修正结果和交付顺序

- `completion-protocol.ts`：保留 Executor 的普通文字结果；缺少格式信息不能自动认证完成；只核对声明的交付事实。
- `subtask-attempt-runner.ts` 与 `attempt-terminal-service.ts`：保存真实终态和核对结果，重复提交同一 Attempt 只生效一次。
- `workspace-publication-worker.ts`：Git 集成和用户文件交付分开记录；交付失败进入“需要处理”，恢复时只补交付，不重做 Executor。
- `control-kernel.ts`：根据结构化事实决定继续、等待、需要处理或结束，不增加内容质量审查。

### 第五步：删除重复恢复逻辑并做商业化验收

保留必要的取消、租约和崩溃恢复，删除重复的状态判断、恢复按钮和前端关键词分支。测试必须覆盖真实的异常顺序，而不是只测正常路径。

## 7. 商业化发布前的硬性验收

以下任一项未通过，都不能把版本作为商业化稳定版本发布：

### Executor 一致性

- MetaWork 与直接调用使用同一协议、模型、工具、工作区、权限和输入；
- Pi、Codex 受影响路径都能实际完成读、写、命令和声明的外部动作；
- 发现运行条件不一致时，任务在启动前明确失败，不显示“执行中”或“等待容量”。

### 状态和并发

- 两个小任务执行、第三个等待时，整体是“执行中”，第三个是“等待中”；释放名额后只启动一次；
- 一个小任务失败时，独立小任务继续，依赖它的任务明确等待或需要处理；
- Executor 已退出后不会一直显示执行中；页面、Dashboard、TUI、飞书和重连状态一致；
- 查询、新消息和取消操作不被后台任务的状态错误锁住。

### 结果和交付

- 只要求回答的任务不生成额外文档；
- 要求文件、代码修改或外部动作时，只核对相应交付物；
- 没有必要结果时不能凭空显示完成；
- 用户文件交付失败时不会显示普通完成，恢复只补交付；
- 重复恢复、取消和迟到结果不会重复执行或复活任务。

### 发布质量

- 受影响的 Kernel、Runtime、TaskView、Gateway、Web 和存储测试全部通过；
- 有故障注入测试：等待、Executor 失败、结果保存失败、文件发布失败、重启、重复点击和取消竞争；
- 当前已知失败测试必须先明确修复或删除错误预期，不能带着红灯发布；
- Docker、Desktop、飞书等未运行的平台逐项标明未验收，不能用主机单元测试代替；
- 源码、安装包和用户安装验收分开记录。

## 8. 明确不做

- 不新增 Execution Manager、第二调度器或第二套状态系统。
- 不要求所有任务产出 Markdown、报告或其他文档。
- 不增加第二个模型复评 Executor，也不建设通用自然语言验收器。
- 不为了通过测试继续保留明显错误的状态和恢复设计。
- 不把一次成功案例当作整个产品已经稳定。
- 不在已知核心故障未关闭时发布商业化版本。

## 9. 关闭条件

方案只有在以下结果全部完成后才能标记完成：

1. MetaWork 调用 Executor 的关键运行条件与直接调用一致。
2. 用户只看到四种主状态，且所有客户端来自同一投影。
3. 局部等待和局部失败不冻结无关分支。
4. 没有结果或声明交付物时不凭空确认成功；不强迫无文档任务生成文档。
5. 文件交付失败可以单独恢复，不重做已完成的 Executor 工作。
6. 已知核心测试问题全部关闭，故障注入和受影响平台验收通过。
7. 代码、当前技术文档和发布说明中的行为一致。
